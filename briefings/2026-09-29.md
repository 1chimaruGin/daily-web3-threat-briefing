## 2. 🟠 Ongoing — carried forward

### Bitget — Third-Party Zero-Day → Forged Admin Credentials → Pre-Signature Transaction Forgery, ~$387.5M (Day 6)

**Chain:** Multi-chain exchange infrastructure (Ethereum, BNB Chain, Avalanche, TRON, Zcash — ETH, BNB, AVAX, USDT, USDT0, USDC, XAUT, XRP, ZEC, TRX reported)
**Status:** ONGOING recovery (Day 6, from **Sept 24** detection). The loss figure is unchanged at **~$387.5M**, but the root-cause description meaningfully sharpened this window. CEO Gracy Chen disclosed that the attacker **exploited a zero-day in an unnamed third-party security product** to obtain **valid, high-level internal admin credentials** — not a compromised private key. Using those credentials, the attacker first ran two sub-threshold **test transfers at 18:31 UTC on Sept 24** (0.184 ETH and 193 TRX, both below Bitget's risk-control alert thresholds), then between **18:58 and 20:09 UTC** executed **17 larger transactions across multiple chains totaling ~$361M**. Bitget's reconciliation system flagged the discrepancy within **7 minutes** (by 19:05 UTC), but the funds were already moved. Independently, security firm **Halborn** published a technical writeup classifying this as a **pre-signature transaction-forgery / infrastructure-authentication-bypass attack**: the forged withdrawal commands were injected into backend wallet infrastructure *before* cryptographic signing, then routed through Bitget's legitimate approval pipeline as if genuine — meaning multisig/HSM key protections were irrelevant because the thing describing the transaction to the approval flow was compromised, not the signers. Bitget says all internal credentials have been invalidated and reissued, the affected third-party vendor has been notified, and private keys/cold wallets were never touched. **Ethereum withdrawals resumed on schedule at 08:00 UTC today (Sept 29)** across Ethereum, BSC, Arbitrum, Base and Optimism, following Bitcoin's Sept 28 resumption; USDT is next at 08:00 UTC Sept 30, with everything else targeted for Oct 2. North Korea attribution remains company-alleged (CEO cites past impersonation attempts by suspected Lazarus-linked actors) rather than independently forensically confirmed; the Mandiant/SlowMist investigation continues.
**Bug class:** access-control / supply-chain (third-party security-product zero-day yielding forged admin credentials that fed pre-signature transaction data into a trusted approval pipeline).

## 4. 🎯 What to hunt

**1. Third-party/vendor components inside the transaction-approval path (sharpened by today's Bitget disclosure)**

The new detail matters for scoping: Bitget's attacker didn't breach the exchange's own code — they hit a zero-day in a *third-party security product* to get admin credentials, then used those credentials to forge pre-signature transaction data that a legitimate approval pipeline accepted as genuine. For any custody, multisig, or MPC system in scope, explicitly map every third-party product (security tooling, monitoring agents, HSM management software, IAM/SSO providers) that has write access or credential-issuing power anywhere upstream of signing — a vulnerability in any of them is functionally equivalent to a key compromise, without ever touching key material. Halborn's framing is the sharpest one-liner for this: "transactions are only immutable and authenticated after they're digitally signed" — anything that can inject or modify data before that point is in scope regardless of how well the signing step itself is protected.

**2. Risk-control threshold testing as a detectable pre-attack signal**

Bitget's own timeline shows the attacker ran two deliberately sub-threshold test transfers (0.184 ETH, 193 TRX) roughly 27 minutes before the real attack began — an attempt to confirm the forged-command pipeline worked without tripping alerts. When reviewing an exchange's or custodian's anomaly-detection design, ask whether it can catch a *pattern* of small-value probes preceding a real attack, not just single-transaction threshold breaches; a purely per-transaction threshold system is blind to exactly this reconnaissance step.

**3. Marketplace/UI-level mitigations papering over unpatchable contract bugs (Magic Eden/Limit Break, Day 6)**

Unchanged guidance: Payment Processor V2 remains callable by anyone, forever, on every chain it's deployed to. Any other integrator of the same unpausable contract remains fully exposed regardless of what OpenSea's flagging system does.

**4. Post-mortem latency as its own signal**

Bitget, Neutron, Payy, Meter.io and Blink are all now 6+ days old (Neutron a full week) with no published full technical root-cause report, despite repeated "in the next few days" commitments. Don't wait on official post-mortems to reason about root cause from on-chain evidence and third-party analysis (as Halborn did for Bitget) — the underlying bug classes are already public knowledge, and contracts/infrastructure sharing the same pattern are exploitable today.

**5. Governance-cost-to-TVL ratio in Cosmos-SDK/CosmWasm chains (Neutron, Day 7)**

Unchanged from prior briefings: for any CosmWasm protocol in scope, calculate the ratio between the cost of winning a governance vote at spot price right before tally and the value of assets that vote's outcome can control, and check for timelocks between proposal tally and execution. `MsgUpdateAdmin`-style chain-governance overrides of app-level multisig protection are a durable pattern, not a one-off.

**6. Client-side signing implementations in hardware/software wallets — treat early figures as a floor (DCENT, Day 15)**

DCENT's XRP leg has now run two full weeks with the signing-compromise mechanism still undisclosed. Prioritize signing/key-derivation code review in any hardware or mobile wallet audit, and don't anchor on a project's first-reported loss number.
