## 1. 🔴 Active exploits (last 24h)

### Harmony ONE — Rollback Execution Day 2 (Aug 18–19): Database Swap Underway

**Chain:** Harmony ONE (PoS, cross-shard)
**Status:** CRITICAL / EXECUTION PHASE — Validator coordination for the database replacement is active as of Aug 19. Bridge.harmony.one remains suspended; no reactivation timeline.

**What happened (recap for context):** On August 12 at 23:25:40 UTC, an attacker exploited a cross-shard receipt validation flaw in Harmony's consensus layer. The bug allowed the attacker to forge valid-looking cross-shard receipts by constructing a bitmask that *counted* public keys without verifying any of those keys had actually signed the message — zero valid signatures required. Over six transactions, 3.01 trillion ONE tokens were minted into four attacker-controlled wallets. At ~26% supply inflation, 97% of forged tokens reached exchange deposit addresses before the bridge was halted; price fell 37% to ~$0.00077.

**Rollback execution (new Aug 18–19):**
- **Target checkpoint:** Shard 0 block 92,730,034 · Shard 1 block 94,978,278 — both at 23:25:37 UTC Aug 11
- **Chain restart height:** Shard 0 block 92,730,035 · Shard 1 block 94,978,279
- **Approach:** Full database replacement (not standard revert) to prevent residual cross-shard index and snapshot artifacts that could preserve the attack surface or cause validator state divergence
- **Client version:** v2026.1.2 — configured to reject the forged block hashes, preventing any validator from inadvertently re-accepting the compromised chain history
- **Discarded:** 109,126 regular user transactions + 315 staking transactions
- **Validator action required NOW:** Install replacement database, upgrade to v2026.1.2, restart consensus from checkpoint

**Secondary risks from rollback execution (new hunter angle):**
- Any transaction valid *before* the rollback checkpoint can be **replayed** after chain restart if protocols on Harmony lack independent nonce/sequence guards in their cross-chain message handlers
- Bridges or L2s that committed to a Harmony state root *after* block 92,730,034 are now anchored to orphaned state — operators must verify their light client roots match canonical chain
- Governance votes, snapshot.org checkpoints, and on-chain airdrops recorded after the rollback target are **erased** — protocols with treasury multisigs that executed txs in this window need to re-execute

**Bug class:** logic-error (signature bitmask counted keys without ecrecover verification)

### Coldcard Bitcoin Entropy Exploit — Day 20: Still No Compensation, Migration Underway

**Chain:** Bitcoin
**Status:** ONGOING — No new confirmed sweep wave in the Aug 18–19 window. Coinkite has not published a victim compensation framework. On-chain data shows ~210K BTC have been migrated to fresh seeds since initial disclosure (users self-rescuing).
**Cumulative losses:** ~$116–130M (5,200+ addresses; 15+ independent attackers; 4 confirmed sweep waves since July 30)

**Root cause (unchanged):** Firmware v4.0.1 (March 2021) replaced hardware TRNG with a weak software PRNG during seed generation, collapsing effective entropy from 128 bits to ~40 bits — brute-forceable offline with no physical device access.

| Device | Affected firmware | Required action |
|---|---|---|
| Coldcard Mk3 | v4.0.0 – v5.0.3 | **Move ALL funds immediately — no firmware fix possible** |
| Coldcard Mk4 / Mk5 | < v5.6.0 | Upgrade ≥ v5.6.0, fresh seed, migrate funds |
| Coldcard Q series | < v1.5.0Q | Upgrade ≥ v1.5.0Q, fresh seed, migrate funds |

> Seeds generated using manual dice-roll entropy are **not** affected. Any seed created via on-device generation on Mk3, or pre-upgrade Mk4/Mk5/Q, must be treated as fully compromised regardless of offline storage.

**Bug class:** key-management (PRNG entropy collapse in firmware)

## 2. 🟡 New disclosed findings / techniques

### Post-Rollback Replay Attack Surface on Harmony ONE (New Research — Aug 19)

**Pattern:** A chain rollback creates a **temporal replay window**: any signed transaction submitted before the rollback checkpoint block can be re-broadcast to a restarted chain if the receiving contract does not maintain its own sequence counter or nonce independently of chain-level nonces.

**Where this bites in DeFi:**
- **Cross-chain message handlers** (bridges, LayerZero, IBC) that check only the chain-level tx nonce but not an internal per-message sequence — a pre-rollback `executeMessage(...)` call can be replayed after chain restart
- **Permit/EIP-2612 signatures** issued before the rollback checkpoint are still valid after restart if the token contract's nonce mapping was erased in the rollback (since the rollback discards all on-chain state after the checkpoint, including used permit nonces)
- **Multisig off-chain signatures** (Gnosis Safe) can be replayed if the Safe's nonce was reset by the rollback
- **Governance votes** scheduled to execute after the checkpoint block: execution transactions discarded by rollback can be retried against restored pre-rollback contract state, potentially triggering unexpected behavior

**Hunting targets:** Any protocol deployed on Harmony ONE should be examined for: (a) whether their cross-chain message handler has an internal sequence counter that survived rollback, and (b) whether their `nonces` mapping (ERC-20 permit, multisig, governance) held state that was erased.

**Bug class:** signature-replay

## 4. 🎯 Hunt hooks

**1. Replay-protection audit for Harmony ONE deployed protocols (URGENT while rollback executes)**
If any protocol you audit has contracts deployed on Harmony ONE: verify whether the contract maintains its own internal nonce/sequence that was preserved through the rollback checkpoint (i.e., was last written before block 92,730,034 on shard 0). Cross-chain message handlers are the highest priority — look for any `execute()` or `receiveMessage()` function that relies solely on chain-level tx sequencing for replay protection rather than an internal message ID map. An internal `mapping(bytes32 => bool) processedMessages` written *after* the rollback checkpoint is now erased; those messages are replayable.

**2. Signature bitmask / quorum pattern — go hunt this on live bridges today**
The Harmony exploit is the canonical 2026 example of "counted keys in bitmask ≠ verified signatures." Actively audit any custom multisig, bridge DVN, or IBC light client that: (a) represents the signer set as a packed `bytes` or `uint256` bitmask, (b) counts set bits to determine quorum, and (c) uses `ecrecover` or `ed25519_verify` in a *separate* loop. The critical question: can quorum pass if the `ecrecover` loop is short-circuited by an empty input or mismatched array length? Target contracts: LayerZero DVN endpoint, Axelar CGP verification, Wormhole guardian set validation, any homegrown bridge using `SignatureVerifier.sol`-style patterns.

**3. Coldcard migration completeness — check staking protocol addresses**
DeFi protocols that allow users to set a withdrawal address (liquid staking, vaults, yield aggregators) may still have victim Coldcard addresses registered as beneficiaries. As a hunter: check whether the protocol exposes a user-updatable withdrawal address and whether there is any rate limiting or delay protecting address changes — a Coldcard victim who migrates funds but forgets to update their registered withdrawal address in a staking protocol remains exposed to fund diversion when rewards next distribute.
