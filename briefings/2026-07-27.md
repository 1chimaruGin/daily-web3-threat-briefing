## 2. 🟡 New Disclosed Findings / Techniques

### 2.1 CertiK H1 2026 "Wrench Attack" Report — Physical Coercion Claims $124M at Record Pace

**Published:** CertiK / CryptoTimes (July 23, 2026)
**Bug class:** `key-management`
**Chains affected:** All — this is an off-chain, physical-layer attack

CertiK's H1 2026 report documents that **physical coercion attacks against web3 personnel** — colloquially termed "wrench attacks" (threatening physical harm to compel a target to hand over private keys, seed phrases, or authorizations) — claimed approximately **$124M in the first six months of 2026**, putting 2026 on pace for an all-time annual record.

**Key findings:**

- H1 2026 produced the highest-ever 6-month wrench-attack total, surpassing the prior full-year record.
- Attacks increasingly target **mid-tier holders and team members rather than founders**, reflecting attacker intelligence-gathering from social media, LinkedIn, and conference attendance records.
- Home invasions of known protocol team members and traders rose sharply; attackers routinely research on-chain wallet balances to select high-value targets.
- Attacks are increasingly sophisticated, involving surveillance periods of weeks before the coercion event.

**Why it matters for hunters:**

Most bug bounty programs are scoped to on-chain vulnerabilities, but several programs (Immunefi, Cantina, HackerOne) now include architectural security reviews as in-scope. The wrench-attack surface exposes a broader governance/operational question: **what happens if a key-holder is coerced?** Hunters reviewing lending, bridge, or staking protocols should document:

1. Whether a single compromised signer (e.g., multi-sig member) can authorize a drain without timelock.
2. Whether "dead man's switch" or guardian veto mechanisms exist that a coerced signer cannot override alone.
3. Whether key rotation can be triggered by surviving council members quickly enough to stop a drain.

### 2.2 AI / LLM-Decompiler Pipeline Now Systematically Sweeping Unverified Contracts

**Pattern source:** Chainalysis (published June 10, 2026); reinforced by BeInCrypto analysis (late July 2026)
**Bug class:** `unverified-contract`
**Chains affected:** Ethereum (primary), BNB Chain, Polygon, Arbitrum

Chainalysis documented five protocols in H1 2026 where the exploited contract was **unverified on its block explorer at time of exploit**, with combined losses of **$36.7M**. The pattern has since been amplified by new BeInCrypto reporting that describes automated attacker pipelines chaining decompilers with LLMs.

**The attack pipeline:**

```
1. On-chain scan: enumerate all contracts with TVL > $X (Etherscan API, Dune, Nansen)
2. Filter: keep contracts with no verified source code
3. Decompile: Dedaub / Heimdall / Panoramix → readable pseudo-Solidity
4. LLM analysis: feed decompiled output into GPT-class model, prompt for:
   - Reentrancy paths
   - Access control gaps
   - Integer arithmetic wrapping
   - Missing pauses / emergency stops
5. Auto-triage: rank by estimated exploitability × TVL
6. Manual review (minutes, not days) on high-scoring hits
7. Exploit
```

**Largest known case:** Truebit on Ethereum ($26.2M, January 2026) — the targeted contract had been unverified on Etherscan since 2021 but continued to hold user funds. The vulnerability was an integer overflow in a pricing function; the attacker used the pipeline to find it in a contract that had never been audited because it appeared "old and quiet."

**Why older Solidity contracts are disproportionately at risk:**

- Pre-0.8.0 contracts lack built-in overflow checks; `SafeMath` was optional and sometimes absent in early DeFi contracts.
- Many early contracts were never verified because Etherscan verification was not yet standard practice.
- Protocols "upgraded around" these contracts rather than migrating users out — leaving legacy code live with TVL.

## 4. 🎯 Hunt Hooks

### Hook 1: Unverified Contract Inventory — Run the Attacker's Own Sweep on Your Targets
*Tied to §2.2 — AI/LLM-decompiler pipeline targeting unverified contracts*

Attackers are now running systematic TVL-weighted sweeps of unverified contracts. You can run the same sweep defensively against your bug bounty targets — and beat them to the finding.

**What to do:**

1. **Enumerate unverified contracts with TVL.** For any EVM target, use Etherscan's API or Dune Analytics to list all contracts in scope that have no verified source. Filter by those holding > $50K in assets or receiving/sending significant transaction volume.

2. **Decompile and review the suspicious ones.** Feed the bytecode into [Dedaub's decompiler](https://app.dedaub.com/) or Heimdall-rs. Look specifically for:
   - Functions that transfer ETH/tokens without a prior ownership/role check
   - Math operations that could wrap (pre-0.8.0 or assembly blocks)
   - `delegatecall` into a non-verified implementation contract
   - External calls before state updates (reentrancy indicator)

3. **Flag the "old and quiet" contracts.** The Truebit case is the archetype: deployed 2021, unverified, still holding $26M. Check the deploy date and whether there's been any protocol upgrade work that "moved around" this contract rather than replacing it.

**Report condition:** Unverified contract with TVL, containing an arithmetic overflow / access-control gap / reentrancy path identified via decompilation → severity proportional to TVL and exploitability. The lack of source verification itself may be a Medium-level finding in programs that require it per their security policy.

### Hook 2: Physical-Layer Key Exposure — Governance Coercion Tolerance Test
*Tied to §2.1 — CertiK $124M wrench attack report*

Multi-sig and Security Council setups assume honest-but-potentially-compromised signers. But the wrench attack model assumes a signer who is **temporarily coerced** — they sign anything asked, then the coercion stops. The question for hunters is: what would a coerced signer be able to do, and how fast?

**What to check:**

1. **Threshold vs. drain speed.** For a 2-of-5 multi-sig: if an attacker coerces 2 signers simultaneously or sequentially, what is the minimum time-to-drain? Is there a timelock? A timelock of 24h+ gives the remaining 3 signers a window to veto — but many protocols have timelocks only on governance proposals, not on treasury outflows.

2. **Emergency withdrawal path.** Does the protocol have an emergency `pause()` callable by a single signer? If so, a coerced signer could *block* an attacker — good. But also check: can a single signer call `unpause()` or `setGuardian()` to remove emergency protections? If yes, that signer becomes a coercion target.

3. **Key rotation speed.** If a signer is coerced and then alerts the team, how quickly can the multi-sig be reconfigured to remove that signer? If rotation requires a quorum vote through the same compromised governance, rotation is blocked.

**Report condition:** Multi-sig or admin key setup where (a) 1–2 signers can authorize an immediate treasury drain with no timelock, **or** (b) a single signer can disable emergency protections with no 2nd-sig requirement → High to Critical architectural finding for protocols with bounty programs covering operational security.

### Hook 3: Bridge DVN / Validator Key Concentration — July Pattern Recap
*Ties together AFX Trade §1.1, Verus (Jul 23–24), Wanchain (Jul 22)*

Three of July's largest bridge hacks — AFX Trade ($24.15M), Verus ETH Bridge ($7.54M, second exploit of the same vulnerability class), and Wanchain ($10M) — all shared a common structural root: **too-few validator keys controlling too-large an outflow, with no on-chain rate limit**.

**Fast checklist for any bridge target:**

| Check | Risk if absent |
|---|---|
| Minimum validator quorum ≥ 5 (preferably ≥ 7) | 2-of-3 or 3-of-5 = small social engineering surface |
| Signing keys held in HSMs / MPC, not raw cloud secrets | Key exfiltration = instant full bridge drain |
| Per-epoch or per-hour withdrawal cap enforced on-chain | No cap = attacker drains everything in one transaction |
| Source contract verified on both origin and destination chains | Unverified bridge contracts can be forked and re-exploited silently |
| Multi-party key rotation on compromise suspicion | No rotation = attacker retains drain capability indefinitely |

The Verus case is particularly notable: the **same vulnerability class was exploited twice** (May 2026 and July 23, 2026, by different attackers). If a bridge has been exploited and the root cause was a class of bug (not just a single instance), hunters should look for **other entry points using the same pattern** — not just the patched call path.

**Report condition:** Bridge with fewer than 5 validator keys OR no on-chain withdrawal velocity cap → High; bridge with same vulnerability class as a prior exploit still present in adjacent code paths → Critical.
