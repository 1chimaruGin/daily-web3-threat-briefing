### Coldcard Bitcoin Hack — Day 11: ~$130M+, 210k BTC Leaving Old Wallet Formats

**Chain:** Bitcoin
**Cumulative losses:** ~$130M+ (Galaxy Research estimate; TRM Labs confirmed ~$116M / 1,816 BTC across 5,200+ addresses; a suspected fourth wave may raise total to ~2,055 BTC / ~$130M)
**Status:** Active sweeping continues. No arrests. No fund seizures. No confirmed recoveries. Multiple independent attacker groups (15+) still racing through the weak-entropy keyspace.

**Day 11 developments:** CoinDesk data from August 7 shows 210,000 BTC (~$13 billion) moved on-chain from legacy wallet formats in the wake of the Coldcard disclosure — the largest mass self-custody migration event in Bitcoin's history. Most moves appear to be legitimate holders securing funds, not attackers. A small fraction of stolen BTC (64.9 BTC via Wasabi + 200 ETH-equivalent via Tornado Cash as of Aug 4) has been laundered; the majority of attacker-controlled addresses remain stationary, suggesting the attackers are waiting out blockchain analytics before moving.

**Technical root cause (unchanged):**

A March 2021 firmware commit introduced an `#ifndef` guard that tested whether a constant was *defined* rather than whether it was *nonzero*. Coinkite had defined the guard constant as `0` ("off"), but `0` is defined — so seed generation silently routed to MicroPython's Yasmarang software PRNG instead of the STM32 hardware TRNG. The result:

| Device | Affected firmware | Entropy |
|---|---|---|
| Mk3 | v4.0.0 – v5.0.3 | ~40 bits (design: 128 bits) |
| Mk4 / Mk5 | < v5.6.0 | ~72 bits |
| Q series | < v1.5.0Q | ~72 bits |

Seeds created via the **dice-roll entry option** are unaffected; that path bypasses the PRNG.

**Remediation (urgent if not yet done):**
- **Mk3:** No firmware patch possible. Move all funds to a new seed on any different device NOW.
- **Mk4/Mk5/Q:** Update to ≥ v5.6.0 / v1.5.0Q **and then generate a new seed and migrate funds**. Firmware update alone is insufficient — the old seed retains compromised entropy.

**Bug class:** key-management

### BTCPay Server LND Macaroon Auth-Bypass — Day 2: Patch Is Not Enough

**Chain:** Lightning Network (Bitcoin)
**Status:** v2.4.2 patch released August 7 closes the vulnerable Greenfield API endpoint. **The threat is NOT fully resolved** — stolen macaroons remain valid unless explicitly rotated.
**Confirmed drained:** Foundation (hardware wallet maker) and Citadel21 (Bitcoin publication) had Lightning nodes swept; channels force-closed, balances drained.

**What operators must do beyond patching:**

The Greenfield API endpoint that leaked `.macaroon` files without completing 2FA verification has been removed in v2.4.2. However, LND macaroons are bearer credentials — they do not expire and are not invalidated when the originating endpoint is patched. An attacker who obtained your admin macaroon before Aug 7 retains full LND admin access.

**Rotation procedure:**
1. Update to BTCPay Server ≥ v2.4.2 (if auto-upgraded interactively, macaroons were regenerated automatically during restart).
2. Check LND macaroon directory timestamps: files in `~/.lnd/data/chain/bitcoin/mainnet/` should be newer than Aug 7 00:00 UTC. If they're older, the upgrade didn't trigger a full restart.
3. Force rotation: stop BTCPay + LND, delete `admin.macaroon` and `readonly.macaroon`, restart LND (it regenerates them), then restart BTCPay.
4. Audit LND payment logs for unauthorized channel closures or payments since ~Aug 1 (conservative window).
5. Operators who cannot patch immediately: take BTCPay offline — a running vulnerable instance is a complete drain risk.

**Technical pattern:** Greenfield API 2FA enforcement had a path where the middleware checked for a valid session cookie but returned a pre-rendered credential response before the check completed under specific request shapes (method + missing cookie combination). This is a middleware short-circuit pattern — the check ran but the guarded response was already staged. Full technical details withheld by BTCPay pending broader operator uptake.

**Bug class:** access-control, key-management

### Wanchain Cardano–BNB Bridge — Day 20: Post-Mortem Still Pending, Hunt Window Still Open

**Chain:** Cardano ↔ BNB Chain
**Status:** Aug 6 white-hat return deadline expired with no fund return. Law enforcement engaged. Technical post-mortem not yet published by Wanchain or BlockSec.
**Unrecovered:** ~$10–13M / 515M NIGHT tokens.

**Root cause (established, full post-mortem still pending):** The bridge's cross-chain message verifier concatenated 14 variable-length redemption fields via `abi.encodePacked` without separators or length prefixes, allowing an attacker to reuse a single legitimate 3,110-NIGHT BNB-side signature to authorize a 203M+ NIGHT Cardano-side withdrawal — a 65,000× amplification via field-boundary manipulation.

**Hunt window:** The post-mortem publication will saturate this pattern publicly. While it remains unpublished, you have a clear-field window to audit bridge contracts in your scope for the same pattern. See Hunt Hook #2 for the exact check.

**Bug class:** signature-replay

## 2. 🟡 New disclosed findings / techniques

### ChainDrop npm Worm — Day 6: Still Self-Propagating, Scope Unclear but 1.3B+ Monthly Downloads Compromised

**What it is:** ChainDrop is a self-propagating supply-chain worm first detected August 4, 2026 at ~09:40 UTC. It is an evolved descendant of the Shai-Hulud npm worm, with enhanced credential-harvesting and EtherHiding C2.

**How it spreads:** Upon compromise of a target maintainer's npm credentials, ChainDrop:
1. Injects a hidden `preinstall` hook (`setup.mjs`) into the maintainer's packages.
2. When a developer or CI/CD runner installs any affected package, `setup.mjs` downloads a temporary Bun runtime and executes a heavily obfuscated payload (`Math_Symbol.js`).
3. The payload harvests npm tokens, cloud credentials (AWS/GCP/Azure IMDS), CI/CD secrets (GitHub Actions tokens, CircleCI, etc.), and Web3 wallet mnemonics / private keys from environment variables.
4. Stolen npm tokens are used to repeat the infection on any other packages the maintainer controls — self-propagation.
5. All exfiltrated data and commands are relayed through on-chain Ethereum transaction calldata (EtherHiding) to avoid domain-based blocking.

**Scale (as of Day 6):** Reports vary — StepSecurity (Aug 4 18:10 UTC) counted 444 packages / 2,212 versions; Aikido puts the floor at 868 packages / 1,381 versions; Bleeping Computer and Infosecurity Magazine cite 1,300+ packages / 2 billion+ monthly downloads. The true count is still uncertain as npm continues pulling versions.

**Highest-risk confirmed packages:**

| Package | Weekly downloads |
|---|---|
| `keyv` | ~150M |
| `flat-cache` | ~150M |
| `file-entry-cache` | ~148M |
| `cacheable` | ~130M+ |

**Why it matters for Web3:** Any developer machine or CI/CD runner that executed `npm install` on an affected package version between Aug 4 09:40 UTC and Aug 4 13:20 UTC (initial containment) should be treated as fully compromised. Private keys, mnemonic phrases, deployment wallets, and protocol admin keys stored as environment variables or in `.env` files were likely exfiltrated.

**Immediate actions for protocols in your scope:**
1. Check `package-lock.json` or CI logs for any of the above packages installed Aug 4 09:40–13:20 UTC.
2. Rotate **all** private keys and npm tokens associated with affected machines.
3. Review GitHub Actions secrets for exposure — especially `DEPLOYER_PRIVATE_KEY`, `ADMIN_MNEMONIC`, protocol-owned multisig signing keys.
4. Audit any contracts deployed from affected CI pipelines in that window for unauthorized ownership transfers.

**Bug class:** supply-chain, key-management

## 3. 🟢 Advisories / CVEs

### CVE-2026-40072 — web3.py SSRF via CCIP Read / EIP-3668 (Day 27 — Broadly Unpatched)

**Affected:** `web3` (Python/PyPI) ≥ 6.0.0b3, < 7.15.0 and ≥ 8.0.0b1, < 8.0.0b2
**Severity:** HIGH (CWE-918 — SSRF)
`handle_offchain_lookup` and `async_handle_offchain_lookup` perform unsanitized HTTP requests to gateway URLs supplied by smart contracts (EIP-3668 / CCIP Read). An attacker controlling a contract can redirect these calls to AWS IMDSv1, GCP/Azure metadata endpoints, internal RPC nodes, or private APIs.
**Fix:** `pip install "web3>=7.15.0"` or `"web3>=8.0.0b2"`. New config options: `ccip_read_allow_http` and `ccip_read_url_validator`.
**GitHub Advisory:** GHSA-5hr4-253g-cpx2
**Status Day 27:** Oracle relayers, bridge backends, and indexers running Python backends remain highest-risk. The affected version range spans most production deployments; patch uptake has been slow.

**Sources:**
- [SentinelOne Vulnerability Database — CVE-2026-40072](https://www.sentinelone.com/vulnerability-database/cve-2026-40072/)

## 4. 🎯 Hunt hooks

**1. ChainDrop blast radius in protocol CI/CD — check for compromised deployer keys.**
If any Web3 protocol in your scope uses npm in CI/CD, check their public `package.json` or `package-lock.json` for `keyv`, `flat-cache`, `file-entry-cache`, or `cacheable`. If they installed between Aug 4 09:40–13:20 UTC, their deployer private keys and admin mnemonics were likely exfiltrated. Concrete check: (a) look at on-chain deployer activity in the days after Aug 4 — unauthorized contract upgrades, ownership transfers, or unusual treasury movements are your signal; (b) if the protocol has a public Tenderly project or on-chain timelock, check for any pending or executed transactions from Aug 4 onward by the deployer wallet. A protocol whose CI was hit and hasn't rotated keys yet is a live CRITICAL under key-management / supply-chain.

**2. Wanchain post-mortem still unpublished — audit your bridge's field-packing before it drops.**
The 20-day gap since the Wanchain breach means you still have a clear window. For any bridge or cross-chain messaging contract in scope: grep for `abi.encodePacked` in the signing path and manually inspect every packed field. Ask: can I craft two different sets of field values that produce the same packed bytes? Focus on variable-length fields (strings, bytes arrays, dynamic arrays) concatenated without length prefixes. If yes, you likely have a signature-replay / hash-collision bug with a direct bridge-drain PoC path. The correct mitigation is `abi.encode` (ABI-encoding is type-aware and length-prefixed) or an `\x19\x01` EIP-712 structured-hash approach. Critical finding on any bridge.

**3. LND Lightning node macaroon rotation lag — hunt unrotated credentials in scope targets.**
For protocols in your scope that run BTCPay or other Lightning infrastructure: check their public BTCPay version (the `/misc/info` endpoint returns the version if accessible). If still on < 2.4.2, that is an in-scope CRITICAL under access-control with a direct drain path via the published Greenfield API auth-bypass. If on ≥ 2.4.2 but macaroons weren't rotated (e.g., unattended Docker upgrade, CI restart), test whether LND admin API calls succeed without an authenticated BTCPay session — an orphaned pre-patch macaroon session still accepted by LND is a full-drain credential, exploitable even with the endpoint closed. File under key-management / access-control with direct reference to the BTCPay August 2026 incident as precedent.
