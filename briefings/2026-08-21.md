### MAYAChain — Six-Bug Chained Logic Exploit (Day 2 of Halt, Aug 21)

**Chain:** MAYAChain (Cosmos SDK / THORChain fork)
**Status:** NETWORK HALTED (Day 2) — No restart timeline published as of Aug 21. All cross-chain swaps suspended. CACAO remains depressed ~89% from pre-exploit levels.
**Cumulative impact:** ~$1.7M extracted by attacker ($1.36M moved to external chains, ~$291K held on-chain); pool TVL impact ~$10.9M (price collapse + arbitrage).

**Aug 21 developments:**
- Team is working through patches for all six identified vulnerabilities in the slash-subsidy and liquidity-pool accounting paths before restarting.

5. Single-tx multi-message structure kept manipulation in one block → price oracle not triggered
6. Slip-based fee protection calculated against *post-inflation* pool depth → rendered ineffective

### Harmony ONE — Rollback Execution Day 4 (Aug 21)

**Chain:** Harmony ONE
**Status:** CRITICAL / EXECUTION (Day 4) — bridge.harmony.one suspended; mainnet still halted at Shard 0 block 92,753,555. No confirmed restart time.

**Aug 21 update:** A portion of the validator set has not yet completed the database-swap to the pre-exploit checkpoint databases (Shard 0: block 92,730,034; Shard 1: block 94,978,278). The rollback requires near-unanimous validator participation before the chain can resume. Validators running v2026.1.2 but still awaiting the replacement database download are the primary bottleneck. The team has urged remaining validators to expedite the swap.

**Risk for returning developers:** Any contract state written after the rollback checkpoints (23:25 UTC Aug 11) will be **erased** post-restart. Key surfaces:
- `nonces` mappings and processed-message sets (replay risk: erased messages are replayable)
- Multisig nonce counters (a transaction executed post-checkpoint may re-execute post-rollback)
- `processedMessages` maps in bridge/cross-shard contracts (double-spend risk)

**Root cause recap:** Bitmask `ecrecover`-bypass — consensus-quorum check counted keys present in a packed bitmask without verifying that any of them *signed* the message. Six transactions minted 3.01T ONE tokens.

**Bug class:** logic-error (bitmask key counting without signature verification), signature-replay (post-rollback nonce erasure)

## 2. 🟡 New disclosed findings / techniques

### Multi-Bug Chain Exploit Pattern: When Individually Low-Impact Bugs Compose Into Critical Exploits

**Pattern:** The MAYAChain attack provides a textbook case of *vulnerability chaining* — a technique where no single bug is independently exploitable at high impact, but sequencing them produces catastrophic results. The six bugs in isolation were: an incorrect outbound-tx monitoring flag (informational), an uncapped arithmetic expression (medium), a lack of per-message price updates (low), a slip-fee calculation scope error (low), a missing pool-depth ceiling in the compensation formula (high), and missing single-block manipulation guards (medium). Combined into a single 23-message transaction, they became a ~$1.7M exploit.

**Why this matters for hunters:**

1. **Standard triage filters miss these.** Most audit pipelines and automated tools flag individual bugs as low-to-medium severity and deprioritize them. A chained exploit depends on human analysis that traces *data flow across multiple functions*, not just per-function severity scoring.

2. **Cross-module interaction surfaces are the highest-value target.** The MAYAChain exploit crossed three modules: the outbound-tx monitor, the slash-subsidy calculator, and the LP accounting module. Bugs that live at cross-module handoffs — where module A's output is trusted as module B's input — are disproportionately dangerous.

3. **Single-transaction bundling is the attacker's force multiplier.** In any protocol where multiple operations can be packed into a single atomic transaction or message batch, an attacker can stack side-effects from earlier messages to influence the behavior of later ones — all within a single block, before any cross-block circuit breaker can trigger.

**Hunting checklist:**
- In THORChain/MAYAChain forks: trace every call path into `compensatePool` / `slashPool` — does the input come from a monitoring function that can be spoofed? Is there an upper bound relative to `pool.depth`?
- In any AMM or cross-chain swap protocol: does the pool price snapshot update *per-message* or only per-block? Can multi-message bundling bypass your slip protection?
- In Cosmos SDK custom modules: do your `EndBlock` or `BeginBlock` handlers trust state set by `MsgServer` handlers in the same block without re-validating?

**Bug class:** logic-error

### Blockchain-as-C2-Infrastructure: NullReceiver Technique (DPRK, Aug 2026)

**Pattern:** In early August 2026, researchers disclosed a DPRK-linked npm supply-chain campaign using a new command-and-control technique codenamed **NullReceiver**. The malware encodes the attacker's C2 IP address directly in the bytes of the *recipient address field* of a zero-value, zero-data Ethereum transfer from an attacker-controlled wallet. The infected package (impersonating a Tailwind CSS plugin) looks up the attacker's wallet, reads the recipient address of its most recent outbound transaction, decodes the C2 IP from those bytes, and connects — all at package install/initialization time.

**Why this is new:** Prior blockchain-based C2 (EtherHiding) stored payloads in contract bytecode or `eth_call` return data — flaggable by static analysis or unusual RPC calls. NullReceiver uses a vanilla `eth_getTransactionByHash` call against a mundane wallet, making it much harder to distinguish from legitimate price-feed or analytics lookups.

**Affected packages (now removed from npm):** `bianira-ui@1.27.0`, `fluid-type-ui@2.0.8`; a follow-up Sonatype investigation found six additional packages with the same payload embedded (including three hijacked legitimate packages).

**Mitigation:**
- Run `npm audit` and verify package provenance before install.
- Flag any dependency that calls `eth_getTransactionByHash` or `eth_getTransactions` outside of explicitly blockchain-related packages.
- Set up egress monitoring for npm-installed code making outbound connections to new IP ranges at install time.

**Bug class:** supply-chain (DPRK / Contagious Interview campaign)

## 4. 🎯 Hunt hooks

**1. Compensation / restitution paths in cross-chain AMMs — hunt uncapped arithmetic TODAY**

The MAYAChain pattern is reproducible in any DEX or cross-chain protocol that has an automated "make whole" path for liquidity providers when node theft or slippage is detected. The critical question is: **does the compensation formula have a ceiling relative to pool depth?** Search your targets for any function that:
- Writes to a pool balance, LP unit count, or `depth` field
- Is called from a slashing, penalty, missing-tx, or insurance-payout handler
- Accepts inputs that an attacker can influence (e.g., a "missing tx" flag set by the protocol's own monitoring logic)

If `payout = f(missingAmount)` with no `min(payout, poolDepth)` or `require(payout <= poolDepth)` guard, it's likely vulnerable to the same class. THORChain, RUNEfi, Vultisig-derived codebases, and any Cosmos SDK chain with custom LP modules are high-priority.

**2. Check for "fixed in one chain, left unfixed in another" flash-loan oracle bugs**

The Allbridge replay demonstrates a recurring failure: a critical bug patched on Chain A but not Chain B. When hunting any multi-chain DeFi protocol, look for:
- Asymmetric deployment histories: was the security fix deployed to *every* chain simultaneously?
- Single-pool price oracles (no TWAP) on any chain the protocol supports
- Flash-loan boundaries: can a flash loan from a lending protocol on the same chain reach the target AMM's pool in the same transaction?

Check the protocol's git history and deployment records. If a `CHANGELOG` or post-mortem from a prior exploit lists a fix, verify the fix was deployed to the *same version* on every chain.

**3. Audit your npm dependency tree for Ethereum RPC calls at install time (NullReceiver)**

Any npm package that calls an Ethereum RPC endpoint during `postinstall`, module initialization, or package load is suspicious. Specifically:
- `npm pack --dry-run` and inspect `preinstall`/`postinstall` scripts for `eth_getTransactionByHash`, `eth_getBlock*`, or `eth_call` targeting external wallet addresses
- Use `strace` / `dtrace` or network capture on `npm install` runs in sandboxed CI environments to flag unexpected outbound HTTPS to Ethereum node providers
- Cross-reference the wallet address from which the transaction is queried — DPRK NullReceiver campaigns reuse attacker wallets across packages, and the GBHackers investigation shows that the attacker wallet is often publicly traceable
