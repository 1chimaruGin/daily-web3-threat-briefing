## 2. 🟡 New disclosed findings / techniques

### Wanchain — Non-Injective Signed-Message Encoding (signature-replay via encoding ambiguity)

BlockSec Phalcon published a full root-cause breakdown of the Wanchain Cardano bridge exploit. The TreasuryCheck validator built its signed message by **raw-concatenating 14 variable-length redeemer fields without delimiters or length prefixes**. Because different field-value tuples can produce the exact same byte string → same Keccak-256 hash → the same valid ECDSA signature, the attacker found an existing legitimate signature (authorizing ~3,110 NIGHT) and rearranged field boundaries to authorize 203,001,692 NIGHT — a **65,000× amplification** — with no new signing required.

This is **not a cryptographic break**: ECDSA was not cracked. The failure is in how the message payload was constructed. EIP-712 structured-data hashing explicitly defends against this by including type hashes and domain separators that make the mapping injective (one input → one hash). Protocols that roll their own binary message encoding — particularly bridges that marshal multi-field authorization messages off-chain — are vulnerable to this pattern.

**Generalizes to:** Any bridge, oracle, or multi-sig protocol where the signed payload is built from variable-length fields concatenated without ABI-style length encoding, type hashes, or field separators. Look for: custom `encode()` or `pack()` functions in off-chain validator code, raw `abi.encodePacked()` on variable-length fields in Solidity, or binary message construction in Go/Rust bridge validators.

**Applies to:** Cardano bridge validators, Cosmos/IBC relayer message signing, any off-chain keeper or guardian that constructs authorization messages outside of EIP-712.

**Source:** [BlockSec Phalcon on X — root cause disclosure (Jul 21)](https://x.com/Phalcon_xyz/status/2079443108027421183); [CryptoTimes — Signature Flaw Behind Wanchain's $10M Exploit](https://www.cryptotimes.io/insights/wanchain-night-bridge-exploit-signature-flaw/)

### CVE-2026-40072 — web3.py SSRF via CCIP Read (supply-chain / SSRF)

`web3.py`'s `handle_offchain_lookup` and `async_handle_offchain_lookup` functions perform HTTP requests to URLs returned by smart contracts during EIP-3668 (CCIP Read) **without any URL validation, allowlisting, or filtering of sensitive destinations**. An attacker who controls the gateway URL field in a smart contract can redirect these requests to:

- Cloud metadata services (AWS IMDSv1 at `169.254.169.254`, GCP, Azure) → credential theft
- Internal RPC servers, private APIs, or admin tooling → SSRF pivot
- Arbitrary external hosts → data exfiltration

The attack surface is any backend service (relayer, oracle feeder, keeper bot, SDK wrapper) that calls into web3.py `offchain_lookup` while processing user-supplied or unvetted contract data.

**Affected:** `web3` (PyPI) < 7.15.0 and < 8.0.0b2  
**Fix:** `pip install "web3>=7.15.0"` (stable) or `web3>=8.0.0b2` (beta). Two new config options land in the patch: `ccip_read_allow_http` (controls HTTP protocol access) and `ccip_read_url_validator` (custom URL validation hook).  
**Note:** This CVE was quietly listed in late July; many projects are unaware because CCIP Read is often considered a "client convenience" feature rather than a security-sensitive call path.

**Source:** [SentinelOne Vulnerability DB — CVE-2026-40072](https://www.sentinelone.com/vulnerability-database/cve-2026-40072/)

## 4. 🎯 Hunt hooks

**1. Check signed-message encoding in bridge validators for non-injectivity**  
In any cross-chain bridge target: find where the authorization message is constructed for multi-party signing. Ask: are variable-length fields delimited? Does the implementation use EIP-712 structured hashing, or raw concatenation / `abi.encodePacked`? Specifically look for `abi.encodePacked(field1, field2, ...)` where any of `field1, field2` are `bytes`, `string`, or dynamically-sized arrays — this is the Wanchain bug class in Solidity. In off-chain validators (Go, Rust, Node), look for `Buffer.concat()` or byte-array join on multi-field payloads without explicit separators. If two different input tuples can produce the same encoded byte string, an existing valid signature can be repurposed for a larger or different authorization.

**2. Audit web3.py CCIP Read in keeper / relayer infrastructure**  
If your targets use any Python-based oracle feeders, keeper bots, or relayers that fetch off-chain data via EIP-3668 CCIP Read — check the `web3` version. Any version < 7.15.0 is vulnerable to SSRF via a malicious gateway URL returned by a smart contract. Test: find the `handle_offchain_lookup` call site and trace what URL validation (if any) is applied before the HTTP request fires. A bug report here could be HIGH/CRITICAL impact if the keeper runs in a cloud environment with access to instance metadata.

**3. DPRK laundering cadence watch — 100/10/1 ETH batch pattern**  
The Drift exploiter's July 23–24 Tornado Cash activity follows the canonical DPRK batch pattern: rapid-fire deposits in 100 ETH, 10 ETH, and 1 ETH denominations from a single consolidating address. At least 107,165 ETH (~$204M) remains in holding wallets. If you operate a protocol with significant ETH TVL and on-chain monitoring, add detection for large ETH inflows from wallets matching this denomination pattern — these wallets are known, labeled, and should be treated as poisoned funds requiring blocking at the contract or frontend level.
