## 2. 🟡 New disclosed findings / techniques

### AI-Assisted Exploit Development Against Unverified Smart Contracts

**Pattern:** Chainalysis H1 2026 analysis found that **$36.7M was stolen from protocols whose source code was never publicly verified** — attackers decompiled raw EVM bytecode and used AI tooling to identify exploitable patterns at scale. This is now an industrialized capability: LLMs can ingest decompiled bytecode from Etherscan's unverified contract section, identify vulnerability fingerprints (reentrancy guards missing, unchecked return values, integer operations without SafeMath), and generate working PoC exploits faster than manual review.

**Why this matters now:** The attack surface for AI-assisted exploitation is specifically the unverified-contract long tail — the thousands of protocols that deployed without verifying source on block explorers. A protocol can have passed an audit and still be unverified on-chain; the decompiled bytecode is a noisier attack surface than source, but AI denoises it.

**What changes for hunters:**
- Unverified contracts with significant TVL are NOW higher-priority targets than verified contracts with similar TVL, because attackers are concentrating AI-tooled effort there
- Tools: [Dedaub decompiler](https://app.dedaub.com/), [Heimdall-rs](https://github.com/Jon-Becker/heimdall-rs) (Rust-based EVM decompiler), [ethervm.io](https://ethervm.io/) for quick bytecode inspection
- If you find a vulnerability in an unverified contract through bytecode analysis, the report documentation burden is higher — include decompiled bytecode evidence. Immunefi and most programs accept bytecode-based reports with decompiled pseudo-code as supporting evidence

**Bug class:** unverified-contract
**Sources:**
- [Chainalysis — Attackers Exploiting Unverified Smart Contracts](https://www.chainalysis.com/blog/attackers-exploiting-unverified-smart-contracts/)

### Hardware Wallet RNG Attestation Gap — The Generalizable Coldcard Pattern

**Pattern:** The Coldcard exploit root cause is a **build-configuration error** (not a deliberate design flaw) that silently swapped the entropy source from hardware TRNG to a weak software PRNG without any runtime error or user notification. The wallet continued to generate seemingly valid seeds — just from a collapsible 40-bit entropy space instead of the designed 128-bit space.

**The generalizable pattern:** Any hardware wallet that:
1. Has a conditional entropy source (hardware TRNG preferred, software PRNG as fallback)
2. Does not verify and attest to the actual entropy source used during seed generation
3. Does not reject or explicitly warn when falling back to software entropy

...shares this structural risk. The seed generation process should be **attestable**: the device should sign a proof that hardware entropy was used, and that proof should be verifiable before the user trusts the seed.

**Applicable scope:**
- Hardware wallet firmware with multiple entropy paths (common in FIDO2/HSM devices too)
- Any protocol that relies on client-generated randomness without verifiable entropy attestation
- Solidity contracts that call `block.prevrandao`, `block.timestamp`, or `blockhash` for randomness — weak entropy is a known contract-level issue too

**Bug class:** key-management
**Sources:**

## 4. 🎯 Hunt hooks

**1. Unverified-contract TVL screen — AI attack surface mapping.**
For every target protocol in your scope: check whether their core contracts are source-verified on Etherscan/Blockscout. Any contract with >$1M TVL that lacks verified source is now actively in the crosshairs of AI-assisted decompilation attacks. Use Dedaub (`app.dedaub.com`) or heimdall-rs to decompile unverified contracts yourself — you're doing the same thing the attacker does, but first. Focus decompiler output on: (a) external function selectors with no access controls, (b) storage layout patterns suggesting uninitialized proxy implementations, (c) arithmetic operations on token balances without over/underflow guards. A unique finding in an unverified contract is a valid Immunefi report — document with decompiled pseudo-code.

**2. Hardware wallet RNG fallback paths — expand the Coldcard pattern.**
The generalizable vulnerability: conditional entropy source (hardware TRNG preferred, software PRNG fallback) with no runtime attestation or rejection. If your scope includes any hardware wallet firmware or HSM codebase, search for entropy fallback branches: in C/C++ firmware, look for `#ifdef` blocks around entropy source selection, or try/catch patterns around hardware RNG reads with software RNG fallbacks. The critical question: if the hardware RNG fails silently, does the device (a) halt, (b) warn the user, or (c) continue with weaker software entropy? A "c" is a critical finding. For smart contracts: any use of `block.prevrandao`/`blockhash` as primary randomness for security-critical operations is the on-chain analog.

**3. Ether.fi monitoring — first-mover advantage on an emerging story.**
If the Ether.fi breach proves real, the first researcher to identify the root cause from on-chain forensics earns significant community recognition and may find the bug class applies to similar liquid restaking protocols (eETH/weETH architecture, EigenLayer restaking integrations). Start now: pull Ether.fi's core contracts from Etherscan, load them in a local fork, and review the withdrawal/accounting logic for: rounding errors in share calculations, missing access controls on admin functions, and oracle dependency in collateral valuations. The architecture (ERC-4626-like vaults + restaking adapter + withdrawal queue) is a common pattern — any bug found here likely applies to 3-5 other LST/LRT protocols.
