## 1. 🔴 Active Exploits (last 24h)

### 1.1 Triple-A Payment Gateway — Hot Wallet Key Compromise — $9.7M | Key-Management | Multi-Chain

- **Date:** July 24–25, 2026 (UTC); PeckShield alert July 25
- **Chains:** TRON, Ethereum, Polygon, Arbitrum, Solana, TON (6 chains)
- **Bug class:** `key-management`
- **Amount lost:** ~$9.7M (5,227 ETH consolidated at `0x01F8...53b1`)

Triple-A, a Singapore-based fiat-to-crypto payment gateway processing merchant payments across dozens of currencies, had hot wallets across six chains simultaneously drained on July 24–25. PeckShield was first to alert publicly, reporting that 5,226.66 ETH (≈$9.72M at time of report) had been consolidated at a single Ethereum wallet address. The attacker bridged stolen assets from TRON, Polygon, Arbitrum, Solana, and TON to Ethereum before consolidating.

**What we know:**

- The drain unfolded across **all six chains within a compressed window**, indicating the root cause is a compromise of the **operational key management layer** — not six independent per-chain exploits. Either a shared hot-wallet infrastructure, a master key store, a cloud KMS credential, or a central orchestration service was compromised.
- Most stolen funds were transferred on July 24 and July 25; the largest single move was **4,140 ETH** into the consolidation wallet, with additional tranche deposits of 615, 157, 112, 100, 72, and 23 ETH following.
- **Deposits reportedly remained open for more than 8 hours** after the on-chain drain became visible — meaning user funds could have continued flowing into compromised wallets during that gap.
- Triple-A had **not issued a public statement** and had not paused services as of press time.

**Root cause:** Not publicly confirmed; the synchronized multi-chain drain pattern is most consistent with: (a) compromise of a cloud KMS or API key granting signing rights across all chain wallets, (b) exfiltration of a BIP-44 master seed from which all per-chain keys derive, or (c) compromise of a backend orchestration service with signing authority. This is **not** a smart-contract exploit.

**Response:** No official response from Triple-A as of July 25–26 UTC. Attacker funds are in consolidation at `0x01F8...53b1`; no evidence of Tornado Cash routing yet.

## 2. 🟡 New Disclosed Findings / Techniques

### 2.1 Chainalysis Post-Mortem: Drift Protocol $285M — Durable-Nonce Pre-Signing + Fake Collateral Whitelist

**Disclosed:** Chainalysis blog (published ~July 25–26, 2026); original exploit April 1, 2026
**Bug class:** `access-control`, `key-management`
**Chains affected:** Solana (and any chain with analogous governance/admin-key patterns)

Chainalysis published a detailed post-mortem on the Drift Protocol $285M exploit — the largest single DeFi drain in Solana's history — revealing two attack patterns that any hunter working Solana governance targets should understand and test for.

**Attack anatomy:**

**1. Durable-nonce pre-signing (Solana-specific governance attack):**

Suspected DPRK actors spent months socially engineering Drift's Security Council members. The critical technique was exploiting Solana's [durable nonce](https://docs.solanalabs.com/cli/examples/durable-nonce) mechanism — a feature designed for legitimate offline signing (hardware wallets, air-gapped systems) that keeps a transaction valid indefinitely rather than expiring within the standard slot window.

The attackers convinced council members to sign what appeared to be routine admin transactions. Because durable nonces remove the expiry constraint, those signatures remained cryptographically valid for months. The attackers collected them, waited until they were ready to drain, then activated the pre-signed transactions — giving the illusion of authorized admin actions while using signatures obtained through deception.

```
Normal Solana tx:  expires after ~90 seconds (recent_blockhash window)
Durable nonce tx:  NEVER expires — valid until the nonce account advances
```

**2. Fake collateral whitelist → drain real assets:**

Once admin control was obtained, the attackers whitelisted a worthless, artificially-priced token (CVT) as approved collateral in Drift's lending markets — **no timelock, no multi-stage approval, no independent oracle requirement.** They deposited 500 million CVT, borrowed $285M in real assets (USDC, SOL, ETH) against the inflated oracle price, and drained the vaults in minutes.

**Why it matters beyond Drift:**

The durable-nonce vector applies to **any Solana protocol** using multi-sig or Security Council governance where durable nonces are used in admin workflows. The whitelist-as-collateral drain applies to any lending protocol (on any chain) where governance can add new collateral without a mandatory timelock + independent price feed validation.

### 2.2 Multi-Chain Hot Wallet Simultaneous Drain — Payment Gateway Attack Surface

**Pattern surfaced:** July 24–25, 2026 (Triple-A $9.7M)
**Bug class:** `key-management`
**Chains affected:** Any protocol using a shared hot-wallet key store or single-root key derivation across multiple chains

The Triple-A incident illustrates a structurally distinct attack pattern from most DeFi contract exploits: **the hot wallet key management layer as a single point of failure spanning multiple chains simultaneously.**

Payment gateways and cross-chain protocols maintaining operational hot wallets typically rely on one of:
- A cloud KMS (AWS KMS, GCP Cloud KMS, Azure Key Vault) storing per-chain private keys with a shared IAM boundary
- A centralized BIP-44 HD derivation service where one master seed maps to wallets on every supported chain
- A backend orchestration service with signing authority that submits transactions to all chains

If an attacker compromises the cloud KMS credentials, the orchestration API keys, or the master seed, **all chains drain in parallel** — exactly what was seen in Triple-A. The synchronized multi-chain timing (6 chains, single compressed window) is the key forensic signal separating this class of compromise from a per-chain vulnerability.

**Architectural red flags in payment gateway targets:**

| Red flag | Risk |
|---|---|
| Single BIP-44 root → all chain key paths | Single secret = all chains compromised |
| Cloud KMS with global IAM (no per-chain key policy) | One credential breach → all keys accessible |
| No per-chain withdrawal velocity limits in smart contracts | Drain proceeds at maximum speed |
| Deposit ingestion not paused by monitoring alerts | Users fund compromised wallets during breach window |
| Hot wallet balance cap not enforced on-chain | Backend-only limit bypassable by direct contract call |

## 4. 🎯 Hunt Hooks

### Hook 1: Solana Durable Nonces in Governance — Pre-Signing Attack Surface
*Tied to §2.1 — Drift Protocol $285M Chainalysis post-mortem*

For any Solana protocol target with a multi-sig or Security Council, durable nonces in governance workflows represent a critical attack surface that is almost never audited.

**What to test:**

1. **Identify durable nonce usage:** Does the protocol's admin or governance path use `SystemProgram.nonceAdvance` / `SystemProgram.nonceWithdraw`? Check the on-chain nonce accounts — if they're owned by individual signers rather than a program-controlled PDA, that's the risk.

2. **Check timelock presence:** Between a governance proposal passing and an admin action executing, is there a mandatory delay? Without a timelock, a compromised council member can execute immediately.

3. **Collateral whitelist gating:** In any lending or structured-product protocol on Solana, who can add new collateral tokens? If it's a multi-sig without a timelock and without requiring a pre-existing Pyth/Switchboard price feed with minimum liquidity, the Drift attack chain applies.

4. **Price cap on new collateral:** When governance adds collateral, is there a mandatory cap on the maximum LTV until that collateral has demonstrated price stability? Drift had none — attackers assigned an arbitrary oracle price to CVT and borrowed at full LTV immediately.

**Report condition:** Solana lending protocol where governance can whitelist collateral with no timelock + no independent price feed requirement + immediate borrowing at full LTV → governance-drain Critical, severity proportional to TVL.

---

### Hook 2: Payment Gateway Hot Wallet Key Isolation — Check the KMS Trust Boundary
*Tied to §1.1 / §2.2 — Triple-A $9.7M*

Payment gateway and cross-chain service targets are frequently in scope for bug bounties but rarely stress-tested for key management architecture. The Triple-A pattern is repeatable wherever a single credential controls wallets on multiple chains.

**What to look for:**

1. **Single-root BIP-44 derivation:** Does the target derive all chain-specific wallets from one master seed or one root key? Check architecture docs, job postings (DevOps roles often describe KMS usage), or infrastructure repositories if in scope. Single root = all chains compromised together.

2. **Cloud KMS IAM granularity:** If the target uses AWS KMS / GCP KMS, are key policies scoped per-chain (individual key ARNs with separate IAM policies) or is there a single signing identity? A single IAM role with sign permissions across all keys is a single-credential compromise.

3. **On-chain deposit circuit breaker:** Can you trigger a deposit to the target's hot wallet addresses beyond their stated daily cap? If there's no on-chain check blocking overfill — and only an off-chain backend that can be bypassed by calling the receiving contract directly — that's a missing circuit breaker finding.

4. **Incident response delay:** Does the target have monitoring that auto-pauses deposit ingestion when abnormal outflows are detected on any chain? Triple-A's 8+ hour window after breach suggests either no such monitoring or manual-only response.

**Report condition:** Any combination of (a) single-root key derivation, (b) no per-chain withdrawal velocity limits enforced on-chain, or (c) no automated deposit pause on anomalous outflow → architecture finding, Medium to Critical depending on TVL and program scope.

### Hook 3: Multi-Chain Velocity + Circuit Breakers — Systematic Gap Across July Incidents
*Ties together Triple-A (§1.1), AFX Trade (Jul 23), CoinDCX (Jul 18)*

Three of July's largest incidents — Triple-A $9.7M, AFX Trade $24.15M, CoinDCX $44M — all share one structural failure: the drain was large, fast, and **not stopped by any automated rate limit or circuit breaker**. This is a pattern, not coincidence.

**On-chain vs. off-chain limit enforcement (critical distinction):**

```solidity
// ❌ OFF-CHAIN ONLY (bypassed by direct contract call):
// Backend checks a Redis counter before calling withdraw()
// Attacker bypasses backend entirely and calls withdraw() directly

// ✅ ON-CHAIN (enforced by smart contract):
mapping(address => uint256) public withdrawnThisPeriod;
uint256 public constant MAX_DAILY_WITHDRAWAL = 1_000_000e6; // $1M USDC

function withdraw(uint256 amount) external {
    withdrawnThisPeriod[msg.sender] += amount;
    require(
        withdrawnThisPeriod[msg.sender] <= MAX_DAILY_WITHDRAWAL,
        "daily limit exceeded"
    );
    // ...
}
```

**What to check in targets:**
1. Does the withdrawal / bridge function have an on-chain rate limit? Or is the limit documented as "enforced by our backend"?
2. If there's a per-address limit, is it also global? An attacker routing through multiple addresses can bypass per-address limits.
3. Is there a minimum delay between large withdrawals and execution (timelock + finality buffer)?

**Report condition:** Withdrawal path with no on-chain velocity check, or limits enforced only off-chain bypassed by direct contract call → Medium to High, potentially Critical if TVL is large and the gap is clearly exploitable without additional conditions.
