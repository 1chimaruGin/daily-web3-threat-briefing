### Coldcard Bitcoin Entropy Exploit — Day 18: Still No Compensation Framework

**Chain:** Bitcoin
**Status:** ONGOING — Coinkite's victim-compensation framework has not been published as of Aug 17 UTC. No new confirmed sweep wave in the Aug 15–17 window. On-chain migration continues: ~210,000 BTC have left legacy cold storage as holders re-evaluate Mk3/Mk4/Mk5 seeds.
**Cumulative losses:** ~$116–130M+ (5,200+ addresses; multiple waves since Aug 4, 2026)

**Root cause (unchanged):** Coldcard firmware v4.0.1 (March 2021) silently substituted a weak software PRNG for the hardware TRNG during seed generation, collapsing effective entropy from 128 bits to ~40 bits — brute-forceable offline without physical device access.

| Device | Affected firmware | Required action |
|---|---|---|
| Coldcard Mk3 | v4.0.0 – v5.0.3 | **Move ALL funds now** — no firmware fix |
| Coldcard Mk4 / Mk5 | < v5.6.0 | Upgrade ≥ v5.6.0, fresh seed, migrate |
| Coldcard Q series | < v1.5.0Q | Upgrade ≥ v1.5.0Q, fresh seed, migrate |

> Seeds created with dice-roll entropy are **not** affected. Any seed generated on Mk3 or pre-upgrade Mk4/Mk5/Q must be treated as compromised.

**Bug class:** key-management

### Harmony ONE Consensus Exploit — Aug 12 (5 days ago, still active response)

**Chain:** Harmony ONE (PoS, cross-shard)
**Amount:** 4 billion ONE tokens minted (~26% supply inflation); token price -37% to ~$0.00077; exchange losses TBD
**Status:** Emergency hard fork activated at block 51,118,080. Bridge.harmony.one suspended. Chain rollback under consideration as of Aug 12 — no finality declaration yet. 97% of fraudulent tokens reached exchange deposit wallets before freeze response.

**Root cause:** A quorum verification bug in cross-shard receipt validation counted the **public keys listed in a signature mask** rather than validating that those keys actually signed. This allowed the attacker to craft receipts with zero valid signatures that passed the quorum threshold. **Impact:**
- 4B ONE minted ≈ 27× the scale of Harmony's 2023 staking bug (146M improperly minted)
- Emergency patch v2026.1.1 deployed; validator upgrade required
- All RVN analogues apply: **do not accept Harmony ONE confirmations above block 51,118,079 as final until convergence declared**

**Bug class:** logic-error (consensus / signature validation)

## 2. 🟡 New disclosed findings / techniques

### The Signature-Mask Quorum Bypass — Harmony's Cross-Shard Pattern (New Aug 12)

**Chains at risk:** Any consensus mechanism or bridge that uses a bitmask or key-list to represent signers and counts present bits/keys against a quorum threshold — without separately verifying that each represented key produced a valid signature over the specific payload.

**Pattern:** Consensus code counted the public keys listed in a signature mask to check quorum, but never verified that those keys had actually signed the message. An attacker can craft a mask listing enough keys to pass the threshold while providing zero or invalid signatures. The `totalSupply` masking further delayed detection.

**Similar historic patterns:** Nomad bridge (2022, message root pre-initialization allowing copy-paste replays); Ronin Bridge (2022, validator key compromise + insufficient threshold). The Harmony 2026 variant is purely an off-by-one or logic error in the counting step — no key compromise required.

**What to check:** For any system using bitmask-based multisig or weighted quorum:
1. Verify that signature validation iterates over *actual signature objects*, not over the mask or key list
2. Check that the quorum check happens **after** individual signature verification, not before
3. Look for any `totalSupply` or similar endpoint that could lag or be manipulated to delay breach detection

**Sources:**

### Split-Transaction Safety-Limit Bypass — USM Protocol Pattern

**Chains at risk:** Any DeFi protocol that enforces per-call limits (max withdrawal, max slippage, max mint) without a global cooldown or cumulative-position check.

**Pattern:** A per-call numerical limit (e.g., max defund amount per tx) that is not enforced cumulatively across multiple calls in the same block or epoch can be atomically bypassed by splitting the large operation into N smaller calls — each individually valid, collectively exceeding the intended limit. Flash loans provide the capital to hold the position across all N calls.

**What to check:** For any protocol with per-call numeric safety guards:
1. Can the same caller invoke the guarded function N times in one block?
2. Is there a global or per-block accumulator tracking total exposure?
3. Can a flash loan fund the required positions across all split calls within one transaction batch?

### CVE-2025-54070 — OpenZeppelin Contracts Bytes.sol Buffer OOB Read (New Late July / Still Unpatched by Many)

**Affected:** `@openzeppelin/contracts` v5.2.0 – v5.3.x (EVM contracts)
**Severity:** MEDIUM | **Patched in:** v5.4.0
**Advisory source:** SentinelOne Vulnerability Database

`Bytes.sol`'s `lastIndexOf(bytes memory buffer, bytes1 needle, uint256 pos)` function reads uninitialized memory outside buffer bounds when `buffer` is empty and `pos` is not `type(uint256).max`. In EVM, this can read arbitrary calldata or storage slots depending on context. No verified public exploit confirmed yet, but contracts using Bytes.sol in 5.2–5.3 for parsing should be treated as exposed.

**Fix:** `npm install @openzeppelin/contracts@^5.4.0`

**Hunt opportunity:** Protocols built on OZ Contracts v5.2–5.3 that use `Bytes.lastIndexOf` for address parsing, signature decoding, or any security-critical logic. Check deployed bytecode against patched source.

## 4. 🎯 Hunt hooks

**1. Audit bitmask/key-list quorum implementations for signature-count vs. signature-verification confusion.**
The Harmony exploit is a template: any bridge, oracle network, or PoS consensus that uses a bitmask or sorted key list to represent signers needs a two-step check — (a) enumerate signers from the mask/list, then (b) verify each one produced a valid signature over the specific payload. If the code only counts bits set or keys present without calling an ECDSA/Ed25519 verify for each, it's exploitable with zero valid signatures. Check: IBC light clients, LayerZero DVN contracts, Axelar CGP verification, any custom multisig using packed `bytes` to encode signer sets.

**2. Test per-call numeric limits for split-transaction bypass.**
The USM Protocol attack is directly reproducible in any protocol with a `max_per_call` guard that isn't backed by a per-block or per-epoch accumulator. In your targets: find functions with a `require(amount <= MAX_X)` guard. Check whether calling that function N times atomically (via a batch contract or flash loan) with N × (MAX_X / N) bypasses the intent. Priority targets: lending protocol withdrawal limits, stablecoin redemption caps, DEX single-tx slippage guards, bridging daily limits implemented without cooldown storage.

**3. Check all deployed bridge/cross-chain contracts for missing deposit-event verification.**
Both Harmony (cross-shard receipts) and Coreum (XRPL relayer) share the same root: an event/message was accepted as a deposit trigger without verifying it corresponded to an externally initiated transfer. In your targets: (a) find the function that credits a user on the destination chain, (b) trace what input triggers that credit — is it a relay submission, a `receiveMessage` call, or an oracle update? (c) verify that the input is cryptographically tied to a specific on-source-chain event, not just a well-formed message with a valid signature. Bridge contracts that trust relayer-submitted payloads without anchoring to a specific tx hash + block proof are vulnerable to this class.
