## 3. 🟢 Advisories & patches

### SlowMist — "DarkSword" Weaponized iOS Wallet-Attack Framework (Oct 19)

SlowMist published a threat-intelligence report tracing the evolution of **DarkSword**, an iOS exploit framework that has been assembled into a deployable attack kit targeting crypto wallet data. The attack chain is triggered from a malicious Safari webpage and automates exploit delivery, device/Keychain/file/message collection, data exfiltration, and wallet-fund decryption and consolidation. Although the toolkit claims support back to iOS 13, SlowMist's code analysis found the actual working exploit range is narrower: **iOS 18.6-18.7.2 and iOS 26.0-26.1**. Timeline: exploit components became public in March 2026; a "DarkSword-PROV2" variant appeared on GitHub in July; associated attack infrastructure was observed live by late September. **No confirmed victim count or dollar-loss figure was cited in this report** — it reads as an advisory about a live threat capability rather than a confirmed-loss incident. SlowMist's recommended mitigation: anyone who visited a suspicious page on an affected iOS version should treat any exposed recovery phrase/private key as compromised, move funds to a new wallet on a clean device, and revoke outstanding token approvals.
**Bug class:** mobile-exploit-chain / wallet-data-exfiltration (OS-level exploit chain weaponized specifically for crypto wallet theft, not a smart-contract bug).

### THORChain — v3.21 Upgrade to Patch Rujira FIN-Contract Position-Transfer Bug (targeted ~Oct 23)

THORChain plans to execute its **v3.21** upgrade at block height **28,366,100** (estimated ~Oct 23, 2026), which will patch a vulnerability in Rujira Network's FIN contract first disclosed **Sept 26, 2026**: a flaw in the position-transfer function let an attacker transfer a custom concentrated-liquidity position without holding a corresponding one. Node operators paused the Rujira application layer immediately; **no user funds were lost** — only a single position owned by the Rujira team itself was affected. THORChain's base layer was never at risk, since Rujira's products run as smart contracts within THORChain rather than on a separate chain. The upgrade also restores Solana and Zcash trading routes that were paused alongside the exploit response, and includes a 24-hour grace period for borrowers to adjust risk-to-reward ratios before liquidations resume.
**Bug class:** logic-error / position-transfer-validation (missing check that the caller actually holds the position being transferred).

## 4. 🎯 What to hunt

**1. Mobile OS exploit chains weaponized specifically for wallet-data theft (DarkSword pattern, new this window)**

DarkSword is a reminder that the attack surface for wallet security extends well beyond the dApp or wallet-extension code itself: a general iOS exploit, once public, can be repackaged into an automated pipeline that targets Keychain data, local wallet files, and decrypts and consolidates funds — all triggered by visiting a single malicious webpage, no app install required. If you're doing wallet or mobile-wallet security work, treat "is the underlying OS/browser exploit still live on versions our users run" as part of the threat model, not just the wallet app's own code.

**2. Position/balance-transfer functions that don't verify the caller actually holds what they're transferring (Rujira pattern, new this window)**

Rujira's FIN contract let an attacker transfer a concentrated-liquidity position without holding a corresponding one — a missing-ownership-check bug in the same family as access-control bugs, but specific to transfer/assignment functions on structured positions (LP positions, vesting schedules, staking receipts). Any protocol with a custom "transfer this position to another owner" function should be checked for whether it actually validates the sender's current holding of that exact position before the transfer executes.

**3. Off-chain trust points in bridge mint-authorization pipelines (Cysic pattern, standing — still unresolved)**

Cysic's bridge still has not published its root-cause report ten-plus days after the exploit. For any bridge audit: enumerate every component — key, relayer, database, API — whose compromise alone is sufficient to trigger a mint/release with no independent on-chain check, and ask what rate limit or multi-party requirement (if any) bounds the damage when that single point fails.

**4. Share/position accounting that double-counts across a release-then-cancel sequence (UNCX pattern, standing)**

Any vesting, staking, or shared-liquidity contract with separate release/cancel/withdraw paths touching a common share counter should be checked for whether every path that changes a position's share balance also updates every other counter derived from it.

**5. Post-mortem latency as its own signal (standing, reinforced this window)**

Cysic, Gamdom, Meter.io, DCENT, Fetch.ai, MultiversX, Blink, MALT, and GoldPesa all currently lack (or substantially lack) a primary technical post-mortem, and both Cysic's and Gamdom's promised follow-up reports remain unpublished well past their original timelines. Reason from on-chain evidence and third-party analysis (Blockaid, SlowMist, Bitquery, PeckShield, Arkham) rather than waiting for an official writeup that may never arrive in useful detail.
