## 1. 🔴 Active exploits (last 24h)

### Coldcard Firmware PRNG — Wave 3 Escalation — $89M / 4,585 addresses (August 2)

**Chain:** Bitcoin  
**Cumulative losses (waves 1–3):** ~1,367 BTC / ~$89M  
**Addresses drained:** 4,585 (up from 1,196 after Wave 1)  
**Root cause:** (unchanged from yesterday) Coldcard firmware 4.0.0 (March 2021) silently replaced the STM32 hardware RNG with a deterministic software PRNG seeded from predictable chip-level data, collapsing effective seed entropy to ~72 bits (Mk4/5/Q) or ~40 bits (Mk3).

**Wave breakdown:**
| Wave | Date (UTC) | Addresses | BTC drained | Method |
|------|-----------|-----------|-------------|--------|
| 1 | Jul 30 | 1,196 | 1,082.65 BTC (~$70.2M) | P2WPKH, shared collector addresses |
| 2 | Jul 31–Aug 1 | 1,477 | ~76 BTC (~$5M) | P2WPKH, same cluster pattern |
| 3 | Aug 1–2 | 1,912 | ~208 BTC (~$13.5M) | **P2WSH, unique destination per victim** |

**Wave 3 tradecraft shift — the key new development today:**  
Galaxy Research flagged the third wave early August 2. Rather than sending victim funds to a handful of shared P2WPKH "collector" addresses (as in waves 1 and 2, which were trivially clustered by chain analytics), Wave 3 routes *each victim's funds to its own P2WSH (pay-to-witness-script-hash) output*. P2WSH can carry multisignature or time-locked redemption conditions whose scripts only reveal on spend — meaning the attacker's wallet structure, quorum requirements, and exit timing are all concealed until they choose to move funds. This makes OFAC-style address clustering nearly impossible until withdrawal occurs.

**Remediation (unchanged — still urgent for anyone not yet patched):**
- **Mk3 (FW 4.0.1 through 5.0.3):** No patch exists. Move all funds to a new seed generated on different hardware *immediately.* The ~40-bit effective entropy is brute-forceable at scale.
- **Mk4/Mk5 (before FW 5.6.0) and Q (before FW 1.5.0Q):** Apply Coinkite emergency firmware. Then evaluate whether your seed was generated *before* patching — if so, rotate.
- Installing the patch does **not** fix an already-compromised seed.

**Bug class:** key-management

## 2. 🟡 New disclosed findings / techniques

### P2WSH as Attacker Evasion — UTXO-Type Switching to Defeat Chain Analytics

Wave 3's switch from P2WPKH to P2WSH is a meaningful operational-security upgrade for the Coldcard attacker and a technique pattern hunters should internalize for victim-identification work:

- **P2WPKH outputs** encode a single public key hash — one address, one key. Chain analytics tools cluster "change" addresses by address-type consistency and spending patterns. All Wave 1/2 victim outputs were P2WPKH and swept to a small number of collection addresses, producing compact and easily attributable clusters.
- **P2WSH outputs** commit to a *script hash* — the actual redemption script (could be 2-of-3 multisig, an OP_CSV time-lock, or a hash-lock) is withheld until spend time. Until the attacker spends the P2WSH output, analysts cannot determine whether one or multiple parties control the coins.
- Using a *unique destination P2WSH address per victim* eliminates the shared-collector clustering that made waves 1 and 2 trivially attributable. Each victim's coins sit in an isolated UTXO silo with an opaque redemption condition.

**Practical implication:** If you are helping a protocol or exchange build post-exploit attribution tooling, querying only for P2WPKH patterns will miss Wave 3 victims and any future attackers using this approach. UTXO scanning must be type-agnostic, with P2WSH scripts indexed at deposit time (before spend reveals the script).

## 4. 🎯 Hunt hooks

**1. Does your target's Gnosis Safe guardian use a Coldcard Mk3?**  
Wave 3's sweep of smaller balances confirms the attacker is going after the entire vulnerable key space, not just high-value wallets. If any of your bug bounty targets use Coldcard hardware for admin multi-sig, treasury custody, protocol pause, or upgrade guardian keys — and those keys were generated on a Mk3 running FW 4.0.1–5.0.3 — those private keys may be brute-forceable today. Even a 3-of-5 Gnosis Safe is weakened if two or more signers used Mk3 hardware; at ~40 bits of effective entropy, recovering two keys is feasible with a modest GPU cluster. Ask in Discord or docs what device/firmware generated protocol keys. A Mk3-generated key controlling an upgradeable proxy is a potential critical finding.

**2. Scan P2WSH outputs for Coldcard-derived sweeps — type-agnostic UTXO indexing**  
If you are building or auditing Bitcoin bridge deposit monitoring (e.g., tBTC, BadgerDAO, or any protocol that accepts BTC inputs), ensure your address monitoring is output-type agnostic. Wave 3 uses P2WSH, which looks identical to a legitimate multisig treasury deposit on-chain until spend. A bridge or custody solution that whitelists P2WPKH only — or that doesn't index spend scripts for incoming P2WSH deposits — could unknowingly accept stolen Coldcard funds as collateral. That's a protocol-level compliance/risk finding worth flagging.

**3. Bridge "second exploit same flaw" pattern — check recently patched bridges in your scope**  
VerusCoin Ethereum bridge was drained $11.6M in May 2026, patched, and then drained again for $7.54M in July via the identical import-path validation flaw. A "patched" bridge is only safe if the patch *covers every entry point* that exercises the vulnerable logic. For any bridge in your scope that suffered an exploit in the last 90 days, read the post-mortem carefully: does the patch address all callers of the vulnerable function, or only the one used in the original attack? A hunt on the VerusCoin bridge today would look at every external function that calls into bridge import/validation paths — not just the one cited in the post-mortem.
