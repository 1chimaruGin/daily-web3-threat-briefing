## 1. 🔴 Active Exploits (last 24h)

### 1.1 Lien Finance — Permissionless Bond Registration + Count-Check Logic Error — $542K | Logic-Error / Price-Manipulation | Ethereum

- **Date:** July 24, 2026 (UTC)
- **Chain:** Ethereum
- **Bug class:** `logic-error`, `price-manipulation`
- **Amount lost:** ~542,144 USDC

Lien Finance, an Ethereum-based structured products protocol offering fixed-rate bonds and OTC derivatives, was exploited for approximately **$542K USDC** after an attacker introduced a synthetic instrument the protocol dramatically overpriced, then extracted real USDC against it.

**Attack anatomy:**

1. **Permissionless bond group registration:** The attacker deployed an orchestration contract and called `BondMakerCollateralizedEth.registerNewBondGroup()` — an open, ungoverned function — to register a crafted bond group containing a **malicious payoff function** that assigns inflated value to attacker-controlled bond tokens.

2. **Overvalued synthetic minted:** Because the protocol's `_calcRateBondToErc20()` function calculated token value from the registered payoff function without validating its economic legitimacy, the attacker's new bond tokens were assigned an exchange rate far above their true worth.

3. **Flawed count-check in `exchangeEquivalentBonds()`:** When swapping bond tokens against OTC pool USDC, the `exchangeEquivalentBonds()` function was supposed to verify that each bond ID appeared exactly the required number of times in the exchange spec. Instead, it only **counted total exception entries**, not whether each specific bond ID met the per-ID cardinality requirement. An attacker could pass a bundle where one bond ID appeared the "right" total number of times at the aggregate level while individual bond-ID constraints went unchecked — allowing a swap that shouldn't have been authorized.

4. **USDC drained:** The overvalued bonds were swapped via the flawed exchange function against live USDC liquidity in the `GeneralizedDotc` OTC pools, netting ~542,144 USDC. The root cause was flagged independently by DefimonAlerts, exvulsec, and SlowMist.

**Response:** Lien Finance has paused pools. No post-mortem published at time of writing.

## 2. 🟡 New Disclosed Findings / Techniques

### 2.1 Permissionless Synthetic Registration + Count-vs-Membership Invariant Failure

**Pattern surfaced:** July 24, 2026 (Lien Finance $542K)
**Bug class:** `logic-error`, `price-manipulation`
**Chains affected:** Any EVM protocol with open derivative/bond registration and unbounded exchange validation

The Lien Finance exploit combines two related but distinct weaknesses that are worth treating separately since each appears independently in other protocols:

**A. Open registration of synthetic instruments without payoff-function validation**

Any protocol that lets users permissionlessly register new derivative groups (bonds, vaults, tranches, options) without gating what payoff functions they can use is exposed. If the protocol then prices those instruments using the registered payoff function on-chain, an attacker can register an instrument whose payoff function returns arbitrarily inflated values, mint "rich" tokens at near-zero cost, and swap them against real liquidity.

*Where to look:* `registerNewBondGroup`, `createVault`, `addPool`, `deployStrategy` — any function callable by arbitrary addresses that registers a pricing or payoff callback.

**B. Count-check vs. membership-check in exchange validation**

```solidity
// VULNERABLE PATTERN (Lien Finance `exchangeEquivalentBonds`):
function exchangeEquivalentBonds(
    uint256[] calldata bondGroupIds,
    uint256[][] calldata bondIds
) external {
    // ❌ Only checks total count of bond IDs across all groups
    uint256 totalBondCount;
    for (uint i = 0; i < bondGroupIds.length; i++) {
        totalBondCount += bondIds[i].length;
    }
    require(totalBondCount == EXPECTED_BOND_COUNT, "wrong count");
    // ⚠️ Never checks whether each specific bond ID appears the
    //    required number of times — attacker can pad with fake bond IDs
    //    to meet the aggregate count while inserting overvalued bonds
}

// SAFE PATTERN:
function exchangeEquivalentBonds(
    uint256[] calldata bondGroupIds,
    uint256[][] calldata bondIds
) external {
    for (uint i = 0; i < bondGroupIds.length; i++) {
        BondGroup memory group = bondGroups[bondGroupIds[i]];
        // ✅ Verify that bondIds[i] matches group.bondIds exactly
        //    (same members, same cardinality per ID, no extras)
        require(
            _arraysMatchExactly(bondIds[i], group.requiredBondIds),
            "bond ID mismatch"
        );
    }
}
```

This is a **set-vs-sum validation** class of bug — common in token basket protocols, structured products, and any contract that processes multi-component bundles. A count-only check is never sufficient when the identity of each element matters.

### 2.2 Injective Labs GitHub OIDC Pipeline Compromise — npm Supply Chain Attack (July 8 Ongoing Advisory)

**Disclosed:** July 8, 2026 | **Analysis widely published:** July 10–14, 2026
**Bug class:** `supply-chain`
**Chains affected:** Injective (all apps built on `@injectivelabs/sdk-ts`)

On July 8, 2026, attackers with **write access to the Injective Labs GitHub repository** exploited the project's trusted-publisher (OIDC) CI/CD pipeline to publish a backdoored version of `@injectivelabs/sdk-ts` (Injective's official TypeScript SDK, ~50,000 weekly npm downloads) without needing a stolen npm token. The malicious release propagated to **18 related npm packages** within minutes via the monorepo's automatic publish chain.

**What the backdoor did:** The payload, disguised as analytics code, captured wallet mnemonic phrases and private keys the moment a wallet was created or loaded, then exfiltrated them to an attacker-controlled server. The package was live for **under one hour** before detection and removal.

**Why it matters for hunters:**

The attack vector — GitHub OIDC trusted-publisher pipeline compromise requiring only repo write access — is increasingly common and harder to detect than a stolen npm token because npm provenance attestations still resolve to the legitimate repository. Developers trust the green provenance checkmark but it only attests that the code was published from that repo; it does not guarantee the repo's own CI pipeline wasn't subverted.

**Action items (still relevant today):**
- Any developer who ran `npm install @injectivelabs/sdk-ts` or any of its 18 dependents between ~21:00–22:00 UTC on July 8, 2026 should treat all wallet keys and seed phrases in that environment as **compromised** and rotate immediately.
- Audit your `package-lock.json` for any version tagged `@injectivelabs/sdk-ts@X.X.X-poisoned-window` or check npm audit logs for installs from that timestamp range.
- For your own projects: restrict OIDC trusted-publisher pipelines with branch/tag filters; require pinned SHAs on CI actions; add npm publish 2FA as a defence-in-depth layer even with OIDC.

## 4. 🎯 Hunt Hooks

### Hook 1: Permissionless Derivative / Bond Registration — Check the Payoff Gate
*Tied to §1.1 / §2.1 — Lien Finance $542K*

Before auditing the swap and exchange logic in any structured-products or fixed-income DeFi protocol, first answer: **can an arbitrary address register a new bond/vault type?** If yes, the next question is: does the protocol validate what payoff function that new type uses?

**What to look for:**

```solidity
// ⚠️ RED FLAG: permissionless registration with no payoff validation
function registerNewBondGroup(
    uint256[] calldata bondTypes,
    address payoffCalculator  // attacker-supplied callback
) external /* no onlyOwner, no whitelist */ {
    bondGroups[nextGroupId++] = BondGroup({
        bondTypes: bondTypes,
        calculator: payoffCalculator  // ← trusted at swap time with no sanitization
    });
}

// ✅ SAFE: whitelist of approved payoff calculators
mapping(address => bool) public approvedCalculators;

function registerNewBondGroup(
    uint256[] calldata bondTypes,
    address payoffCalculator
) external {
    require(approvedCalculators[payoffCalculator], "calculator not approved");
    // ...
}
```

**Report condition:** Any protocol where (a) bond/derivative group registration is permissionless AND (b) the registered payoff/price callback is used in swap value calculations without a whitelist → High/Critical depending on TVL. The Lien Finance fix will need to either gate registration via governance or whitelist calculators.

---

### Hook 2: Set Validation vs. Sum Validation in Multi-Component Exchanges
*Tied to §1.1 / §2.1 — the `exchangeEquivalentBonds` count-check bug*

Whenever a DeFi protocol processes a **bundle of tokens** in a single exchange call (bond redemption, basket swap, tranche unwrap, structured product settlement), look at what the validation actually checks. Count checks (`require(arr.length == N)`) are almost never sufficient when element identity matters.

**Pattern to grep for in any repo:**

```bash
# Find exchange/swap/redeem functions that check length but not membership
grep -n "\.length ==" contracts/**/*.sol | grep -v "bondIds\[i\]"
```

**Manual check:**
1. Find the exchange/redeem function that accepts an array of token IDs or bond IDs.
2. Check whether validation checks **only the total array length** or verifies that **each specific required ID is present** (using a set membership check, sorted comparison, or bitmap).
3. If only length is checked, construct a PoC where you pass an array of the right length but with an overvalued element substituted in — if the protocol accepts it, it's a finding.

**Report condition:** Multi-element bundle exchange where validation is length-only, not membership-exact → Medium to High depending on whether the attacker can supply an overvalued element and the dollar impact.

### Hook 3: CI/CD Pipeline Trust — OIDC Trusted Publishers for npm Packages
*Tied to §2.2 — Injective Labs GitHub compromise, 18 packages poisoned*

If you're hunting for supply-chain vulnerabilities or participating in programs that include SDK/tooling scope, check the target's npm publishing setup. The Injective attack required only **GitHub repo write access** — no npm token was needed — because the OIDC trusted-publisher relationship was unconditional.

**What to look for in a target's GitHub Actions CI:**

```yaml
# ⚠️ VULNERABLE: unconditional OIDC publish (any push to any branch triggers)
- name: Publish to npm
  uses: JS-DevTools/npm-publish@v3
  with:
    token: ${{ secrets.NPM_TOKEN }}
  # No branch filter — a push to any branch publishes to npm

# ✅ SAFER: restrict publish to protected tags only
- name: Publish to npm
  if: startsWith(github.ref, 'refs/tags/v')
  uses: JS-DevTools/npm-publish@v3
  with:
    token: ${{ secrets.NPM_TOKEN }}
```

**Also check:**
- Does the npm package page show provenance attestations? If yes, does the attested workflow have branch/tag restrictions?
- Does the project require 2FA on npm publish even with OIDC? (2FA as a backstop if the OIDC filter is weak)
- Are GitHub Actions pinned to commit SHAs (`uses: actions/checkout@abc123`) or floating tags (`uses: actions/checkout@v4`) that an upstream maintainer could backdoor?

**Report condition:** High-download web3 npm package with unconditional OIDC trusted-publisher publish on any branch, combined with write access obtainable via PR merge or branch push → supply-chain Critical for any protocol depending on that package.
