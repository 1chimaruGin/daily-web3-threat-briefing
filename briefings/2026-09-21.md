## 2. 🟠 Ongoing — carried forward

### Fetch.ai + NuNet + SingularityNET (AGIX/WMTx) — Stolen Bridge Signing Key, ~$16.77M Attacker Holdings (Day 3)

**Chain:** Ethereum (the exploited bridge's counterpart chain is Cardano)
**Status:** CONFIRMED and now wider than originally scoped. First disclosed **Sept 19** (Fetch.ai/NuNet legs); **widened Sept 20–21** as PeckShield and multiple outlets confirmed the same attacker cluster also exploited SingularityNET's own bridge contract.
**Sept 20–21 developments (why it is still here):** PeckShield identified the actor behind the AGIX/WMTx mints as **the same wallet cluster** that drained FET and minted NTX on Sept 19. On **Sept 20 at 09:42:56 UTC**, the attacker minted **260 million AGIX** and **53.838 million WMTx** via the SingularityNET bridge contract. AGIX crashed from ~$0.0775 to ~$0.0006841 — a **>99% intraday collapse** — wiping roughly **$93M off AGIX's market cap**. Fetch.ai confirmed its own FET contracts remain unaffected and paused AGIX-to-FET conversions as a precaution; World Mobile (WMTx) said it contacted exchanges to freeze affected deposits.

**Recap:** the root cause across all four tokens (FET, NTX, AGIX, WMTx) traces to the same **compromised SingularityNET bridge backend signing/authorizer key**, since this key authorized conversions and mints across the shared cross-chain infrastructure linking the ASI Alliance projects (Fetch.ai, SingularityNET, Ocean/related, NuNet, and partner token World Mobile). One leaked key produced valid-looking authorization for mint/conversion calls across every token routed through that bridge, not just the one it was assumed to gate.

**Attacker holdings (per PeckShield, as of the Sept 20 snapshot):** ~$16.77M combined — **198.3M AGIX (~$14.42M)**, **649 ETH (~$1.67M)**, **33.538M WMTx (~$627K)** — plus the FET/NTX proceeds reported on Sept 19–20. This is the attacker's held balance, not a confirmed total-extracted figure; realized value is lower given AGIX's illiquidity after the crash, and some proceeds may already be laundered through swaps.

**Root cause:** unchanged from the Sept 19–20 analysis — a **single compromised backend/authorizer key** for the SingularityNET bridge, with **no rate limit or per-transaction cap** on the mint/release path (per SlowMist's prior analysis of the asymmetric `conversionIn`/`conversionOut` modifiers). The new information is the blast radius: the same key authorized value release for **multiple tokens sharing the bridge**, not just FET.

**Bug class:** key-management (compromised shared bridge signing key), access-control (no per-token or per-transaction caps on the mint/release path)

### MultiversX — VM-Level Atomicity Flaw, Mainnet Still Halted (Day 3)

**Chain:** MultiversX (EGLD)
**Status:** STILL HALTED. No public confirmation as of time of reporting that block production has resumed. First disclosed **Sept 19**; cause confirmed **Sept 20**. Loss amount still **not disclosed**.
**Sept 21 developments:** none of substance found beyond the Sept 20 position — engineers are still validating the fix on a shadow fork before coordinating a mainnet deployment with validators, exchanges and infrastructure partners; a targeted recovery preserving finalized history remains under evaluation. ## 3. 🟢 Advisories & patches

**No new web3-relevant CVEs or vendor patches were identified in the Sept 20–21 window.** The one item worth flagging is a pattern observation from today's SingularityNET widening rather than a new disclosure.

### Shared bridge keys have a blast radius equal to every token routed through them

**Pattern:** the SingularityNET incident's Sept 20–21 widening shows that a single compromised authorizer key did not just drain one contract — it produced valid-looking mint/conversion authorizations for **every token sharing that bridge's signing infrastructure** (FET, NTX, AGIX, WMTx). Reviewers who scoped the Sept 19 Fetch.ai/NuNet incident as "one converter contract, one key" would have missed that the same key gated three more token economies.

**Hunting checklist for bridge/converter audits:**
- Identify every token, contract and chain that shares a signing key, multisig, or authorizer role with the target contract — not just the target's own direct dependencies.
- For shared-infrastructure bridges (common in token "alliance" or multi-project ecosystems), map the full set of contracts a single compromised key could authorize, and treat that whole set as one blast-radius unit for severity purposes.
- A finding that says "if this key leaks, contract X is drained" is incomplete if the same key also gates contracts Y and Z — the real exposure is the union.

## 4. 🎯 What to hunt

**1. Shared-key blast-radius mapping for any bridge, converter or minter in scope**

This is today's one genuinely new lesson, and it's cheap to apply: before scoping a bridge/converter audit down to a single contract, enumerate every other contract, token and chain that trusts the **same authorizer key or multisig**. Ask what the total combined mintable/releasable value is across that whole set, not just the contract you were handed. The Fetch.ai finding from Sept 19 ("no rate limit on the release path") was correct but undersized — the real severity was four token economies deep, not one.

**2. Modifier-parity sweep on mirrored bridge functions — still the highest-yield cheap check**

Unchanged guidance from prior days, still unresolved industry-wide: for every bridge/converter/vault, diff the modifier lists, amount `require`s, pause checks and signer checks between mirrored function pairs (`conversionIn`/`conversionOut`, `deposit`/`withdraw`, `mint`/`burn`, `bridgeIn`/`bridgeOut`). Any asymmetry favoring the value-out direction is a finding independent of whether a key has actually leaked.

**3. VM/client-layer atomicity — MultiversX is still unresolved and still a live reference case**

MultiversX's mainnet has now been halted for three days on an unpublished VM-level atomicity bug. If your scope includes node, VM or execution-client code, hunt multi-step state transitions that are not applied all-or-nothing, and treat any verification cache (the Liquid Network root cause) as a candidate for a missing-field cache-key bypass. Both of this month's chain-halting bugs came from client/VM code, not Solidity — an underhunted surface relative to its payout.

**4. Collateral listings where borrow capacity exceeds token market cap**

Unchanged from prior guidance: for each listed collateral on a lending market, compute maximum borrowable value against the asset's circulating market cap, and check whether the price oracle is derived from DEX pools an attacker can create or thinly seed. Nostra's market has been paused for five days on exactly this pattern with no resolution yet — a live, still-open reminder that this class remains exploitable in production.
