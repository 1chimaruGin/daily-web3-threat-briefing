## 1. 🔴 Active Exploits (last 24h)

### 1.1 WEMIX — $6.25M Owner-Key Compromise → Unauthorized Stablecoin Mint | Access-Control | WEMIX / Ethereum / BNB Chain

- **Date:** July 26, 2026, ~09:17 UTC (detected); official statement July 27, 2026
- **Chains:** WEMIX (exploit origin), Ethereum, BNB Smart Chain (funds moved)
- **Bug class:** `access-control` `key-management`
- **Amount lost:** ~$6.25M

An attacker gained **owner-level control** over the WEMIX$ stablecoin smart contract and minted **5.23 million WEMIX$** — a completely unbacked issuance that bypassed the protocol's documented mint-control architecture. Per WEMIX's whitepaper, minting of WEMIX$ is restricted exclusively to the `DIOS` stability protocol via an "Authorized Mint Access" gate. The attacker used the seized owner privileges to invoke the mint function directly, overriding that intent entirely.

**Attack flow:**

```
1. Attacker acquires owner-key access to WEMIX$ contract (method: TBI)
2. Direct call to mint() → 5,230,000 WEMIX$ issued outside DIOS path
3. WEMIX$ converted to 30,736 WEMIX + 724,198.27 USDC.e
4. USDC.e bridged to Ethereum and BNB Smart Chain
5. Swapped to ETH + USDT, dispersed across several addresses
6. Some funds deposited directly into centralised exchanges
```

**Protocol response:**

- Bridges paused; liquidity pools paused.
- WEMIX contacted exchanges to freeze attacker-linked addresses; several exchanges cooperated.
- Blockchain security firms engaged for tracing.
- Root cause of the owner-key compromise remains under official investigation — WEMIX warned that initial loss figures may change.

**Why this matters:**

This is WEMIX's **second major security incident in just over a year** (a previous $724K stablecoin hack occurred in 2025). The exploit exploits a structural property common to many Layer-1 ecosystem stablecoin designs: the **owner role can often override the "only minting path" logic** if not explicitly guarded by multi-sig or timelock. Any protocol with an `onlyOwner` modifier on a `mint()` function for a stablecoin or synthetic asset is in the same risk class.

## 2. 🟡 New Disclosed Findings / Techniques

### 2.1 Owner-Role Minting as a Silent Bypass — Stablecoin and Synthetic Asset Pattern

**Pattern surfaced by:** WEMIX exploit (July 26–27, 2026) + community post-mortems
**Bug class:** `access-control`
**Chains affected:** Any EVM with `onlyOwner` on a mint function (particularly L1/L2 ecosystem stablecoins, wrapped tokens, synthetic assets)

The WEMIX incident crystallizes a vulnerability class that is **systematically under-reported in bug bounty programs** because it looks "intentional": an `onlyOwner` modifier on `mint()` is not, by itself, flagged as a bug. But the risk emerges when:

1. The protocol documentation or whitepaper specifies that only a specific internal contract (e.g., a stability module, a bridge contract, or a peg mechanism) should ever call `mint()`.
2. The actual on-chain enforcement only checks `onlyOwner` — it does **not** check that `msg.sender == diosStabilityModule` or similar.
3. The owner key is a single hot key (or a compromised cloud KMS key), not a multi-sig.

An attacker who compromises the owner key can mint unbounded supply, with no on-chain circuit breaker stopping them.

**What to look for:**

```solidity
// Vulnerable pattern: 
function mint(address to, uint256 amount) external onlyOwner {
    _mint(to, amount);
}

// Safer pattern — whitepaper intent matches code:
function mint(address to, uint256 amount) external {
    require(msg.sender == stabilityModule, "Only stability module");
    _mint(to, amount);
}
// Even safer: stabilityModule itself requires multi-sig approval for mints > threshold
```

Check whether **the real-world "only X should mint" constraint is enforced in code** or only in documentation. Protocols where the whitepaper's mint-path intent diverges from the on-chain enforcement are exploitable whenever the owner key is compromised.

### 2.2 Legacy Contract Targeting: Attack Rate Against 1yr+ Old Contracts Tripling in 2026

**Pattern source:** CertiK H1 2026 analysis; SlowMist 182-incident H1 2026 report
**Bug class:** `logic-error`, `integer-overflow`, `unverified-contract`
**Chains affected:** Ethereum (primary), BNB Chain, Polygon

CertiK and SlowMist H1 2026 data confirms a trend now clearly supported by incident data: **the monthly count of exploits targeting contracts deployed more than one year ago rose from 7 in October 2025 to 18 in May 2026** — a ~2.5× increase. Attackers are systematically revisiting legacy codebases rather than hunting only new deployments.

**Why this is happening:**

- AI/LLM-assisted decompiler pipelines (covered July 27 briefing) can now efficiently analyze the entire unverified contract surface at scale.
- Many protocols "upgraded around" legacy contracts (deploying new logic alongside old, or redirecting routing) without migrating TVL out — leaving old code live with significant balances.
- Pre-Solidity-0.8.0 contracts are disproportionately represented: `SafeMath` was optional; assembly arithmetic is common; overflow checks are absent.
- Old contracts rarely have emergency pause mechanisms, meaning no rapid mitigation exists once exploitation begins.

## 4. 🎯 Hunt Hooks

### Hook 1: Stablecoin / Synthetic Asset `mint()` — Whitepaper vs. Code Divergence
*Tied to §1.1 WEMIX $6.25M and §2.1 owner-role minting pattern*

The WEMIX exploit exploited the gap between "only the stability module may mint" (whitepaper) and "`onlyOwner` can mint" (code). This gap is **not a single-protocol quirk** — it is a recurring pattern across L1 ecosystem stablecoins, wrapped tokens, and synthetic assets.

**What to check in your targets:**

1. **Read the whitepaper / docs on minting.** Who is described as the authorized minting entity? Is it a named contract? A stability protocol? A bridge?

2. **Check the on-chain implementation.** Does the `mint()` function check `msg.sender == <specific authorized contract address>`, or only `onlyOwner`/`onlyRole(MINTER_ROLE)`?

3. **Check the MINTER_ROLE or owner address.** Is it an EOA (hot key)? A simple multi-sig with 2-of-5 (or fewer)? No timelock on role assignment?

4. **Check for supply cap enforcement.** Even if the minter is controlled, is there a `maxSupply` or `mintCap` that prevents runaway issuance in a single transaction?

**Report condition:** Documented "only X can mint" constraint that is NOT enforced in contract code — the actual `mint()` relies solely on `onlyOwner` or `onlyRole(MINTER_ROLE)` with the role held by an EOA or simple 2-of-5 multi-sig → High (if owner key is non-MPC/non-HSM) to Critical (if exploitable without key compromise, i.e., role assignment itself is misconfigured).

### Hook 2: Oracle Signature Verifier Assumptions — "Accepted Invalid Signature"
*Tied to Bonzo Lend $9M oracle exploit (July 11, 2026) and ongoing oracle-manipulation trend*

The Bonzo Lend exploit on Hedera was technically caused by the **Supra oracle's on-chain verifier contract accepting an invalid signature** on a price update — a failure in the verifier's input validation, not in Bonzo's own contract. But Bonzo's contract then consumed that manipulated price without sanity-checking the result (a price 12 orders of magnitude above market). The loss was $9M.

**Dual-layer hunt for any oracle-consuming DeFi target:**

**Layer 1 — Is your target's price feed oracle verifier contract verifying correctly?**
- Find the oracle adapter/verifier contract your target uses (Chainlink `latestRoundData`, Supra, Pyth, API3, Redstone, Band).
- For on-chain verifiers (Supra, Pyth, Redstone): read the verifier code. Does it check signature validity with `require(isValidSig, ...)` before returning a price? Does a failed check revert or return a sentinel value that callers might misinterpret?

**Layer 2 — Does your target sanity-check the price it receives?**
```solidity
// Check if the target does THIS kind of sanity bounding:
require(price > MIN_ACCEPTABLE_PRICE, "Price below floor");
require(price < MAX_ACCEPTABLE_PRICE, "Price above ceiling");
require(updatedAt >= block.timestamp - STALENESS_THRESHOLD, "Stale price");
```
If the target trusts the oracle return value unconditionally, a single oracle failure (manipulation, stale data, bad verifier) causes protocol-level damage.

**Report condition:** Missing price sanity bounds on oracle consumption + oracle verifier that can return stale or extreme values → High to Critical depending on TVL and exploitability of oracle data source.

### Hook 3: Multi-Incident Recidivism — "Second Hack, Same Protocol" Pattern
*Tied to WEMIX (second major hack in ~13 months) and Verus Bridge (second exploit of same class, May→July 2026)*

July 2026 has now produced two notable "repeat victim" incidents: **WEMIX** (hacked in 2025 and again July 26, 2026) and **Verus Bridge** (exploited May 2026 and July 23, 2026, same vulnerability class, different attacker). For bug bounty hunters, previously-exploited protocols are **prime targets** because:

- The root cause from the first exploit is often narrowly patched (the specific call path) without systematic review of similar code paths.
- Post-exploit operations are rushed; new code is deployed under time pressure.
- Trust in the post-exploit system by users (and therefore TVL recovery) sometimes outpaces actual security improvement.

**Fast checklist for re-targeting a previously-exploited protocol:**

1. **Find the post-mortem.** What was patched? Is the patch minimal (single-function fix) or structural (role system redesigned)?
2. **Identify the vulnerability class.** Search briefings or audit reports for the root class (e.g., `access-control`, `oracle-manipulation`). Are other contracts in the same codebase using the same pattern?
3. **Check deploy dates of new contracts post-hack.** Were they audited? Many emergency fixes skip audit queues.
4. **Look for the same class in adjacent modules.** If the stablecoin's `mint()` was patched, is the `burn()` equivalently guarded? Does the bridge adapter have the same issue?

**Report condition:** Same vulnerability class as a prior disclosed exploit still present in an adjacent, un-patched contract or code path → Critical (attacker advantage: known entry point, pre-built exploit tooling).
