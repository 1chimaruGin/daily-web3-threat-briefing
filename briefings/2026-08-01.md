## 1. 🔴 Active exploits (last 24h)

### Coldcard Hardware Wallet — Firmware Entropy Flaw — $38M BTC (July 31, August 1 follow-up)

**Chain:** Bitcoin  
**Amount:** ~594 BTC / ~$38M  
**Victims:** ~500 single-signature wallets, many dormant since 2021–2024  
**Timeline:** ~25-minute sweep, July 31, 2026  
**Root cause:** A firmware regression introduced in Coldcard Mk3 firmware **4.0.0 (March 2021)** caused the device to bypass its dedicated hardware true RNG and fall back to MicroPython's software PRNG, seeded from predictable non-secret chip data. Result:

- **Mk3 (FW 4.0.1 through latest):** ~40 bits of effective entropy — computationally feasible to brute-force. *No firmware patch possible for Mk3; keys must be regenerated on a different device.*
- **Mk4 / Mk5 / Q (seeds generated before today's patched firmware):** ~72 bits of entropy — reduced but not immediately practical to brute-force at scale.

Chainalysis published an August 1 report confirming the attacker studied wallet sizes *before striking* — highest-value wallets were targeted first, draining the most BTC per minute of exposure. The 25-minute sweep suggests scripted scanning of the reduced entropy space.

**Affected devices & remediation:**
- All COLDCARD Mk3 (FW 4.0.1+): **Permanently compromised.** Move funds *immediately* to a new seed generated on a different, unaffected device.
- Mk4, Mk5, Q: Apply Coinkite's emergency firmware update (Mk4/Mk5: ≥5.6.0; Q: ≥1.5.0Q), then assess whether seeds were generated *before* the patch. If so, rotate to a new seed.

**Bug class:** key-management

## 2. 🟡 New disclosed findings / techniques

### Coldcard PRNG Fallback — Generalizable RNG-Bypass Pattern in Embedded Firmware

The Coldcard incident reveals a generalizable flaw class in hardware security modules: **conditional RNG fallback with an insecure default path.** The vulnerable code path in firmware 4.0.x called the hardware RNG, but on error conditions — or after a silently failing initialization — fell through to MicroPython's `random` module seeded from chip-level but predictable data. The flaw went undetected for five years across multiple audit cycles because:

1. The output *looked random* in standard statistical tests (the PRNG output was not obviously bad).
2. Entropy budget estimation is rarely tested against known-weak seeds in embedded device audits.
3. Keys generated with weak entropy are indistinguishable from strong ones in normal operation.

**Generalizes to:** Any hardware wallet, HSM, or embedded signing device that uses a software RNG fallback. MPC wallet nodes, Ledger alternatives, and custom signing hardware using embedded Linux or MicroPython-derivative runtimes are in scope. Bug bounty hunters targeting wallet manufacturers: the most impactful class of bug here is a *reachable code path* where entropy collection silently degrades without alerting the user.

**Source:** [In Bitcoin We Trust Substack — The Bitcoin Entropy Nightmare (Jul 31)](https://inbitcoinwetrust.substack.com/p/the-bitcoin-entropy-nightmare-coldcard); [Coldcard Security Notice — TradingView (Jul 31)](https://www.tradingview.com/news/newsbtc:105b214f2094b:0-coldcard-security-notice-puts-bitcoin-wallet-entropy-risk-back-in-focus/)

### AFX Trade Bridge — Aug 3 Goodwill Distribution (Follow-Up to July 24 $24.15M Hack)

AFX Trade has announced a goodwill compensation distribution scheduled for **August 3, 2026** for victims of the July 22–23 bridge exploit. The $24.15M USDC drain stemmed from compromise of five of seven bridge validator signing keys — the attacker reached the 2/3 quorum needed to authorize withdrawals with no on-chain challenge mechanism capable of blocking the transaction within the 200-second challenge window. AFX offered the attacker a 30% bounty (≈$7.2M) to return 70% (~$16.9M); the deadline passed without contact, and the attacker converted all USDC to ~12,467 ETH and moved it to Ethereum mainnet. The August 3 distribution uses protocol treasury reserves.

**Implication for hunters:** The validator key storage model — where 5 of 7 keys can be independently compromised — reflects a common bridge DVN risk. Check bridge validator key custody in targets: are keys in independent HSMs or co-located in the same cloud environment? The latter collapses a multi-sig into a single point of failure.

### Ostium Post-Mortem Confirms Off-Chain Oracle Signer Key Theft (July 30 publication)

Ostium's official post-mortem (published July 30, one day after the July 15 exploit) formally attributes the $23.75M USDC vault drain to **compromise of the off-chain oracle signer private key**. The attacker submitted fraudulent but *cryptographically valid* signed price reports using the stolen key, manufacturing profitable positions that drained the OLP vault. The post-mortem notes the signer key was stored in cloud infrastructure with insufficient access controls — a credential compromise, not a smart contract flaw.

**Why this matters now:** Three of July's top four exploits (Ostium, AFX Trade, CoinDCX/BigONE) share the same root cause: off-chain key compromise feeding into on-chain logic that trusts the key unconditionally. The contracts performed exactly as written; the trust model was wrong.

**Source:** [CryptoTimes — Ostium Post-Mortem Confirms $23.75M Vault Loss, Blames Off-Chain Signer (Jul 30)](https://www.cryptotimes.io/2026/07/30/ostium-post-mortem-confirms-23-75m-vault-loss-blames-off-chain-signer/)

## 4. 🎯 Hunt hooks

**1. Audit all protocol multi-sig and guardian keys for Coldcard Mk3 provenance**  
If any of your bug bounty targets use Coldcard hardware wallets for admin multi-sig, treasury custody, or protocol pause/upgrade guardian keys — and those keys were generated on a Mk3 device running firmware 4.0.1 or later — the private keys may be brute-forceable. Ask in the protocol's docs or Discord: what device and firmware version was used to generate guardian keys? A Mk3-generated key controlling an upgradeable proxy or a significant treasury is a potential critical. Even a strong quorum (e.g. 3-of-5 Gnosis Safe) is weakened if multiple signers used the same vulnerable hardware.

**2. Off-chain signer key storage — the $100M+ attack surface audits ignore**  
Ostium ($23.75M), AFX Trade ($24.15M), and CoinDCX ($44M) all lost funds through off-chain key compromise, not smart contract bugs. When scoping a DeFi target with a keeper, oracle feeder, or bridge validator, *ask how the signing key is stored*: Is it in an HSM? In a cloud secrets manager accessible from multiple services? On an EC2 instance with an IAM role? In plaintext in a `.env` file in a CI pipeline? Protocols rarely document key storage in bug bounty scopes, but infrastructure compromise is now the #1 DeFi attack vector by losses in H1 2026. A finding about insecure signer key storage is legitimately critical-severity even without a smart contract flaw.

**3. Verify bridge validator quorum architecture before marking "audited"**  
Both Wanchain (signature-replay amplification) and AFX Trade (5-of-7 key compromise) demonstrate that a bridge's *validator quorum design* can be exploited independently of its Solidity code. For bridge targets: map out (a) how many validators exist, (b) where their signing keys are stored, (c) whether a quorum compromise could succeed from a single cloud environment breach, and (d) whether the challenge/dispute window is practically actionable. A 200-second window with no automated circuit breaker is a design flaw, not a feature.
