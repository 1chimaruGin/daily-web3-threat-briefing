### Aave v3 — FlashLoopAdapter / Loop Safe Module Access-Control Exploit, ~114.09 ETH (~$305K) (Day 6)

**Chain:** Ethereum (third-party "Loop Safe Module" adapter used alongside Aave v3 and Safe multisig wallets; Aave's and Safe's own core contracts unaffected).
**Status:** UNRESOLVED, now three days past the Oct 3, 18:00 UTC whitehat-bounty deadline (keep 11.41 ETH, return 102.69 ETH). No public confirmation found of whether the attacker accepted, returned funds, or let the offer lapse.
**Root cause (unchanged):** FlashLoopAdapter's `open()`/`close()` functions verified callers only via `ISafe(msg.sender).isModuleEnabled(address(this)) == true` — spoofable with a forged Safe contract that always returns true — combined with an unrestricted arbitrary-call `_swap()` path.
**Bug class:** access-control (trusting a module-enabled check as caller-identity proof, plus unrestricted arbitrary-call path).

**Sources:**

## 4. 🎯 What to hunt

**1. Multisig whitelist/approval toggles as an attack primitive, not just a config action (Base vault, still unclaimed)**

Unchanged from the last edition: the core anomaly is two consecutive, validly-signed Safe transactions (remove attacker contract from whitelist, re-add it 60 seconds later) that no one claims to have intended. For any audit touching a Safe-gated vault, lending whitelist, or module-permission list: check who can change the list, how fast changes can be made after a long period of dormancy (this Safe had been dormant 25 days before the incident), and whether there's any delay/timelock between a whitelist change and that address becoming usable. A permissions list that can be toggled and exploited inside a single block is operationally equivalent to no permissions list.

**2. Hook/rebalance logic that fails to isolate protocol-injected liquidity from caller input (MALT, GoldPesa — still unconfirmed by either team)**

Unchanged: a swap or liquidity-management function that calls an external hook mid-transaction (rebalance, netting, repayment) and then checks only the resulting balance, not who actually supplied each unit of value. Any protocol using Uniswap v4 hooks or similar flash-accounting rebalancing callbacks should verify this explicitly.

**3. Recovery-rate realism vs. attribution headlines (Bitget, Day 13)**

Still only ~$1.1M frozen of $387.5M despite a formal DPRK attribution. Attribution confidence and fund-recovery likelihood remain separate axes for any exchange/custody risk assessment.

**4. Third-party adapters/modules bolted onto audited core protocols (Aave FlashLoopAdapter, Day 6)**

Unchanged: a helper contract trusting a cheap boolean (`isModuleEnabled`) as a stand-in for caller identity, paired with an arbitrary-call path. The victim's on-chain whitehat bounty offer (90% return, 10% keep, hard deadline) remains a useful template to know — the deadline is now three days gone with no public resolution either way, itself a data point on how often these offers actually get taken.

**5. Governance-controlled recovery is not the same as recovery (Neutron, Day 14)**

The Cosmos Hub community voted nearly unanimously to veto returning the recovered 1.23M ATOM to a proposal-submitted address — a reminder that on-chain interception of stolen funds is a necessary but not sufficient step; the actual return path still runs through a political process that can stall or fail entirely.

**6. Post-mortem latency as its own signal (standing)**

Meter.io, DCENT, Fetch.ai, MultiversX, Blink, GoldPesa and MALT still have no primary team write-up, several now weeks overdue. Don't wait on official write-ups to reason from on-chain evidence; also don't assume "no write-up yet" means "nothing happened" — re-check periodically, since Payy's real post-mortem sat unnoticed for several days before being picked up in this briefing series.
