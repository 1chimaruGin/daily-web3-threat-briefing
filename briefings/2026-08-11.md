### Coinsbuy CEX — Aug 9, $7.9M TRON + Ethereum (NEW)

**Chain:** TRON, Ethereum
**Amount:** $7.94M total — 6.04M USDT (8 TRON wallets) + 1.89M USDT + 77 ETH (3 Ethereum wallets)
**Status:** Funds in motion; ChangeNOW froze ~$542K in ETH. ~$6.7M reached instant-exchange services (FixedFloat, ChangeNOW, BingX) then pivoted toward Monero via ChangeNOW — most unrecovered. Exchange refilled drained wallets within 24 hours.

**Attack pattern:** Coordinated two-chain sweep executed ~13:00 UTC Aug 9. Attacker opened with a probe 5 USDT transaction, then emptied eight TRON wallets in ~60 minutes; Ethereum wallets drained simultaneously. Stolen funds cross-chain-bridged via Bridgers within an hour of theft. Roughly 79% of funds routed through 50 single-use FixedFloat addresses to break the on-chain trail before exchange freezes could propagate.

**Root cause:** Not formally disclosed. The fact that Coinsbuy refilled wallets within 24 hours (rather than halting withdrawals indefinitely) suggests the attacker accessed withdrawal infrastructure — likely a compromised hot-wallet API key, admin credential, or internal access vector — rather than owning the private keys outright. No on-chain contract exploit observed.

### Coldcard Bitcoin Hack — Day 12: ~$130M+, 15+ Attacker Groups, Laundering Crawls

**Chain:** Bitcoin
**Cumulative losses:** ~$130M+ / ~2,055 BTC (TRM Labs baseline: 1,816 BTC / $116M across 5,200+ addresses; suspected Wave 4 extension raises estimate to ~2,055 BTC)
**Status:** Active sweeping continues across the weak-entropy keyspace. No arrests. No fund seizures. 15+ independent attacker groups confirmed by blockchain analytics. Minimal laundering: 64.9 BTC via Wasabi + 200 ETH-equivalent via Tornado Cash (as of Aug 4). Most attacker-controlled BTC remains stationary at consolidation addresses.

**Day 12 context:** CoinDesk data from Aug 7 confirmed ~210,000 BTC moved on-chain from legacy wallet formats — the largest mass self-custody migration event in Bitcoin history, driven by legitimate holders securing funds post-disclosure. The migration is making it harder for attackers to identify remaining weak-entropy addresses amid general UTXO churn. Investigation ongoing; FBI and DOJ involvement reported as of Aug 5.

**Technical root cause (unchanged):**

A March 2021 firmware commit introduced an `#ifndef` guard testing whether a constant was *defined* (not whether it was *nonzero*). Coinkite set the guard constant to `0` ("off") but `0` is defined — so seed generation silently fell back to MicroPython's Yasmarang software PRNG instead of the STM32 hardware TRNG:

| Device | Affected firmware | Effective entropy |
|---|---|---|
| Mk3 | v4.0.0 – v5.0.3 | ~40 bits (design: 128 bits) |
| Mk4 / Mk5 | < v5.6.0 | ~72 bits |
| Q series | < v1.5.0Q | ~72 bits |

Seeds created via the **dice-roll entry option** are NOT affected — that path bypasses the PRNG entirely.

**Remediation (urgent if not yet done):**
- **Mk3:** No firmware patch possible. Move ALL funds to a new seed on a different device immediately.
- **Mk4/Mk5/Q:** Upgrade to ≥ v5.6.0 / v1.5.0Q AND generate a new seed and migrate funds. Firmware update alone is insufficient.

**Bug class:** key-management

### BTCPay Server LND Macaroon Auth-Bypass — Day 3: Patch Deployed, Stolen Credentials Still Live

**Chain:** Lightning Network (Bitcoin)
**Status:** v2.4.2 patch (released Aug 7) closes the vulnerable Greenfield API endpoint. The critical residual threat: **stolen macaroons do not expire and are not invalidated by the patch**. Any operator who was compromised before Aug 7 and has not manually rotated LND macaroons retains a live full-admin credential in attacker hands.
**Confirmed drains:** Foundation (hardware wallet maker) and Citadel21 (Bitcoin publication) had Lightning nodes swept and channels force-closed.

**Day 3 status:** No new confirmed drains in the Aug 10–11 window. The attack surface has narrowed to unpatched instances and patched-but-unrotated instances. Both remain fully drainable.

**What operators must still do:**
1. Confirm BTCPay ≥ v2.4.2 is running.
2. Check LND macaroon timestamps — files in `~/.lnd/data/chain/bitcoin/mainnet/` must be NEWER than Aug 7 00:00 UTC. If older, a full restart did not occur.
3. Force rotation: stop BTCPay + LND → delete `admin.macaroon` + `readonly.macaroon` → restart LND → restart BTCPay.
4. Audit LND payment history for unauthorized channel closures or payments since Aug 1 (conservative window).

**Bug class:** access-control, key-management

### Wanchain Cardano–BNB Bridge — Day 21: Post-Mortem Published, No Funds Returned

**Chain:** Cardano ↔ BNB Chain
**Status:** Aug 6 white-hat deadline expired. Law enforcement engaged. Wanchain has now published the official post-mortem.
**Unrecovered:** ~$10–13M / 515M NIGHT tokens. Token down ~30% from pre-hack level.

**Post-mortem confirms (now public):** The bridge's `TreasuryCheck` validator constructed signed messages by concatenating 14 variable-length redeemer fields using `abi.encodePacked` without separators or length prefixes. This is non-injective: multiple distinct field combinations produce identical packed bytes. An attacker reused a single legitimate 3,110-NIGHT BNB-side signature to authorize a 203M+ NIGHT Cardano-side withdrawal — a 65,000× amplification via field-boundary collision. The bug is in smart contract serialization, not the bridge cryptography or validator key management.

**This is now a widely-published pattern** — expect copycat hunting across other bridges this week.

**Bug class:** signature-replay

### ChainDrop npm Worm — Day 7: Scope Partially Contained, EtherHiding C2 Still Active

**What it is:** Self-propagating supply-chain worm first detected Aug 4 09:40 UTC. Descended from Shai-Hulud worm, adding enhanced credential harvesting and Ethereum transaction calldata as C2 channel (EtherHiding — domain-block-immune).

**Day 7 status:** npm has pulled the bulk of malicious versions (containment began ~13:20 UTC Aug 4). Self-propagation largely stopped. However: (a) EtherHiding C2 remains active and is unblockable via domain-based filters; (b) developer machines and CI/CD runners that executed `npm install` in the Aug 4 09:40–13:20 UTC window should still be treated as fully compromised; (c) package count estimates continue to diverge (StepSecurity: 444 packages / 2,212 versions; Aikido: 868+; BleepingComputer: 1,300+).

**Highest-risk confirmed packages (all affected versions pulled):**

| Package | Weekly downloads |
|---|---|
| `keyv` | ~150M |
| `flat-cache` | ~150M |
| `file-entry-cache` | ~148M |

**Stolen material:** npm tokens, AWS/GCP/Azure IMDS credentials, GitHub Actions secrets, CircleCI tokens, and Web3 wallet mnemonics / private keys from environment variables and `.env` files. All data exfiltrated via on-chain Ethereum calldata.

**Immediate actions (if not yet done):**

### Wanchain abi.encodePacked Signature-Replay — Pattern Now Widely Published, Copycat Risk Elevated

The Wanchain post-mortem (see Section 1) makes the `abi.encodePacked`-in-signing-path pattern public and linkable for the first time. Prior to today, the hunt window was exclusive. Now it is open to all hunters simultaneously. Any bridge or cross-chain messaging contract using packed encoding in its signing path without explicit field separators is a target.

**Pattern fingerprint:**
- `abi.encodePacked` used to construct a message that is then hashed and signed
- Two or more variable-length fields (strings, `bytes`, dynamic arrays) concatenated without length prefixes or delimiters
- A mapping from signed message → authorized action (cross-chain transfer, withdrawal, governance action)

**Correct fix:** Replace `abi.encodePacked` with `abi.encode` in the signing path, or use EIP-712 structured hashing (`\x19\x01` + domain separator + struct hash).

**Bug class:** signature-replay
**Sources:**
- [Wanchain post-mortem (Medium)](https://medium.com/@wanchain_org/cardano-bnb-chain-bridge-incident-post-mortem-353e465276e7)

## 3. 🟢 Advisories / CVEs

### CVE-2026-40072 — web3.py SSRF via CCIP Read / EIP-3668 (Day 28 — Broadly Unpatched)

**Affected:** `web3` (Python/PyPI) ≥ 6.0.0b3, < 7.15.0 and ≥ 8.0.0b1, < 8.0.0b2
**Severity:** HIGH (CWE-918 — SSRF)
`handle_offchain_lookup` and `async_handle_offchain_lookup` perform unsanitized HTTP requests to gateway URLs supplied by smart contracts (EIP-3668 / CCIP Read). An attacker controlling a contract can redirect these requests to AWS IMDSv1, GCP/Azure metadata endpoints, internal RPC nodes, or private APIs — extracting cloud credentials or triggering internal service calls.
**Fix:** `pip install "web3>=7.15.0"` or `"web3>=8.0.0b2"`. New config options: `ccip_read_allow_http`, `ccip_read_url_validator`.
**GitHub Advisory:** GHSA-5hr4-253g-cpx2
**Status Day 28:** Patch uptake remains slow. Oracle relayers, bridge backends, and indexers running Python are highest-risk. Most production `web3.py` deployments are in the affected range.

## 4. 🎯 Hunt hooks

**1. Coinsbuy pattern — check CEX withdrawal API access control in scope targets.**
Coinsbuy's attack profile (coordinated multi-chain hot-wallet sweep via what appears to be API/credential access rather than private key theft) matches a recurring 2026 pattern (Triple-A, WEMIX). For any CEX or custodial protocol in your scope: (a) check whether their withdrawal API enforces IP allowlisting, MFA, or rate-limits separately from account login; (b) look for publicly accessible `/withdrawal` or `/transfer` API endpoints without per-request signing — these are increasingly targeted. If you find unsigned or weakly-authenticated withdrawal paths, that's a direct CRITICAL under access-control with a straightforward drain PoC path. TRON hot wallets in particular are being hit repeatedly this month — TRON-based hot wallet access control is your first grep target.

**2. abi.encodePacked signing paths — post-mortem is public, race the field.**
Now that Wanchain's post-mortem is published, other hunters will grep for `abi.encodePacked` in bridge contracts immediately. Your edge is speed and breadth. Concrete check: for every bridge or cross-chain messaging contract in your scope, run `grep -r "abi.encodePacked" --include="*.sol"` and filter for usages inside functions that (a) also call `keccak256` and (b) pass the result to an ECDSA signature verification or a mapping lookup. Any match with two or more adjacent variable-length fields (bytes, string, dynamic arrays) and no length prefixes is a candidate vulnerability. File under signature-replay; severity is CRITICAL on any bridge.

**3. BTCPay + Lightning node unrotated macaroon scan — still in window.**
Three days post-disclosure, most small-operator BTCPay instances have patched but not rotated macaroons. For any Lightning-facing protocol or merchant in your scope: (a) check the public `/misc/info` endpoint for the BTCPay version (pre-2.4.2 = unpatched, instant CRITICAL); (b) if ≥ 2.4.2, check whether the macaroon directory was regenerated by comparing file timestamps against the Aug 7 patch date — an older macaroon is still a live drain credential. An orphaned pre-patch admin macaroon accepted by LND is a full-channel-sweep attack with direct financial impact, reportable under access-control / key-management.
