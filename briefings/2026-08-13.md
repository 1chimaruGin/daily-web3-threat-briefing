### Ravencoin KAWPOW Consensus Bug — Day 6: Active Reorg Under Way

**Chain:** Ravencoin (PoW, KAWPOW algorithm)
**Status:** ACTIVE / IN RECOVERY — not yet resolved as of Aug 13 UTC
**Attacker first block:** Height 4,487,776 — timestamp 2026-08-07 15:44:01 UTC
**Market impact:** RVN hit all-time low ~$0.00276 on Aug 12; -19% from pre-exploit level; market cap ~$47M
**Exchanges:** Upbit, Bitget, Bitvavo suspended all RVN deposits/withdrawals

**Technical root cause:** A bug in KAWPOW block header validation allows an attacker to bypass the normal memory-intensive proof-of-work computation entirely. The vulnerability lies in how `nHeight` (the declared height field embedded in the block header) is validated — vulnerable nodes failed to cross-check the declared height against the block's actual position in the chain. An attacker can set `nHeight` to route validation through a code path that skips full KAWPOW verification, enabling the creation of synthetically "valid" blocks at essentially zero hash cost.

This is Ravencoin's third consensus-layer failure (the two prior ones also involved KAWPOW validation edge cases), and uniquely this time the disclosure team included a working proof-of-concept posted publicly — meaning the exploitable technique is fully public.

**Response:**
- 2Miners shipped emergency patch **v4.6.1.1-hf1** that rejects blocks failing the corrected `nHeight` check and checkpoints at block 4,487,775
- 2Miners + RavenMiner (together commanding a majority of network hash rate) are mining a competing chain from block 4,487,775 onward, deliberately excluding the exploited branch
- If this honest chain accumulates sufficient PoW to become the longest chain, a reorganization covering approximately **72 hours (3 days) of transaction history** will occur — all transactions confirmed after block 4,487,775 on the original chain should be considered potentially reversible
- Core dev team fix status: the emergency patch came from **a mining pool, not the Ravencoin core team**, continuing a pattern from prior consensus failures

**What remains at risk:** Any exchange or protocol that accepted RVN deposits after Aug 7 on unpatched nodes may face reorged confirmations and reversed credit. The fix is node-level — anyone running a Ravencoin full node or accepting RVN payments must upgrade to a version that includes the `nHeight` height-validation fix before trusting confirmations.

**Bug class:** logic-error (consensus layer PoW validation bypass)

### Coreum XRPL Bridge — Day 4: 199,900 XRP Drained via Relay-Signature Forgery

**Chain:** XRP Ledger ↔ Coreum (cross-chain bridge)
**Date exploited:** August 9, 2026 (~97-minute attack window)
**Amount drained:** 199,900 XRP (~$200K at ~$1 XRP price); bridge left with 493.5 XRP (0.3% of reserves)
**Bridge status:** Paused as of Aug 11. No official post-mortem from Coreum Development Foundation as of Aug 13.

**Technical root cause:** The bridge's relayer verification logic accepted fraudulent deposit events as valid when an attacker assembled sufficient relay-node signatures for fabricated transactions. The bridge required 17-of-28 relay-node multisignature approval. The attacker compromised or socially engineered enough relay nodes to gather the 17 required signatures on synthetic (non-existent) deposit events — the bridge software processed these as legitimate XRP deposits and authorized corresponding Coreum-side withdrawals. Across 94 multisignature transactions over 97 minutes, the attacker drained 99.7% of the bridge's XRP reserve.

**Critical distinction:** The XRP Ledger itself and its private keys were NOT compromised. No XRP inflation or protocol-level breach occurred. The flaw is entirely in the **off-chain relayer software** that bridges the two chains — a classic bridge-DVN pattern where the trust assumption is in relayer consensus, not in either chain's cryptographic security.

**Post-exploit:** XRP price dropped below $1 (first time since 2024) following the news; price has partially recovered. Bridge remains paused with no announced timeline for reopening.

**Bug class:** bridge-dvn, unverified-contract (relayer signature-threshold validation flaw)

## 2. 🟡 New disclosed findings / techniques

### Ravencoin KAWPOW: PoW Bypass via Block Header Height Field Manipulation

**What it is:** The KAWPOW proof-of-work algorithm for Ravencoin uses the block height (`nHeight`) as a seed parameter in the hashing computation. Vulnerable node implementations failed to verify that the `nHeight` value embedded in a submitted block header matches the block's actual position in the chain. An attacker setting `nHeight` to a specific value can redirect execution into a validation code path that short-circuits the full KAWPOW memory-intensive computation — producing effectively "free" blocks from the network's perspective.

**Applicability to other PoW chains:** Any PoW chain that (1) uses mining algorithm parameters seeded from block-header fields, and (2) does not cross-validate those fields against chain state during block acceptance, shares this structural risk. Notably:
- Chains that forked KAWPOW (Firo, Meowcoin, Neoxa) should audit their `nHeight` validation
- Any PoW chain with algorithm-variant selection logic based on block-height ranges is worth checking for similar bypasses

**How to hunt it:** In any PoW chain's block validation code, locate where mining-algorithm parameters are derived from block-header fields. Check: (a) is each parameter bounds-checked against expected chain state before being used in PoW verification? (b) Can a submitted block's declared height diverge from its actual chain position without rejection? A "yes" to (b) is a candidate consensus critical.

**Bug class:** logic-error

### Bridge Relayer Threshold Signature Forgery: The Coreum Pattern

**What it is:** The Coreum bridge required 17-of-28 relay-node signatures on deposit events — a threshold multisig scheme. The relayer software accepted any set of 17 valid signatures on an event, regardless of whether the underlying deposit event actually occurred on-chain. The attacker forged deposit events (not real on-chain transactions) and gathered 17 relay node signatures for them, satisfying the threshold check without an actual deposit.

**Root pattern:** Threshold signature schemes in bridge relayers that validate *signature count* without validating *event authenticity* against the source chain's canonical state are vulnerable. The relayer's job is to attest "this event happened on chain A" — if the relayer software can be fed fake events and will sign them, the bridge's entire security model collapses regardless of how well the destination chain's smart contracts are written.

**How to find it:** In any bridge relayer codebase, look for the event-submission flow:
1. How does the relayer determine an event is real? Does it query the source chain's RPC, or does it trust a message from other relayers?
2. If relayers can vote on events without each independently verifying them on-chain, a compromised minority can generate fake events with real signatures
3. Check: can an event be submitted for signing before finality is confirmed? A race between submission and finality allows double-spend-style attacks

**Bug class:** bridge-dvn, unverified-contract

## 4. 🎯 Hunt hooks

**1. PoW block-header field manipulation — the Ravencoin KAWPOW pattern applies beyond RVN.**
Ravencoin's bug is a consensus-layer validation failure: a declared field in the block header (`nHeight`) was trusted without verifying it against chain state. For any PoW layer-1 in your scope, find where mining algorithm parameters are derived from block-header fields, and check: (a) is there an assertion that each header field matches expected chain state *before* it's used in PoW verification? (b) Can the declared height/epoch/period diverge from the block's actual chain position? Chains that forked KAWPOW — Firo, Meowcoin, Neoxa — are immediate candidates. A PoW bypass enabling zero-cost block creation is a consensus-critical bug with direct inflation and double-spend impact. File these as CRITICAL regardless of chain size.

**2. Bridge relayer threshold schemes — replicate the Coreum XRP investigation on your targets.**
The Coreum attack pattern: gather enough relay-node signatures (17/28) on a fake event to satisfy the bridge's threshold check, without a real on-chain deposit. For every bridge in your scope, map the event attestation flow: (a) Does each relay node independently verify the event exists on the source chain by querying a live RPC, or does it sign based on a message from another relayer? (b) Is there a finality window enforced before signatures are collected? (c) Is there a replay-protection mechanism preventing the same event from being submitted multiple times with fresh relay votes? Any "no" is a candidate critical. The threshold-multisig model is only as strong as each node's independent chain verification — if any shortcut exists, the whole model breaks.

**3. Coreum-pattern + Wanchain-pattern together — bridges under immediate pressure.**
The community now has two publicly detailed bridge exploit techniques from the past two weeks (Coreum relay-forgery Aug 9 and Wanchain `abi.encodePacked` signature replay Aug 11). Any bridge with variable-length packed ABI signing AND threshold-based relayer attestation is sitting at the intersection of both known patterns. Run `grep -r "abi.encodePacked" --include="*.sol"` targeting signing paths AND audit the relay node event-validation logic. These are independent bugs that can both exist in the same codebase. The first to file both gets maximum bounty impact.
