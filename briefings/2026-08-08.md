### Coldcard Bitcoin Hack — Day 9: ~$130M Cumulative, Competitive Sweeping Unresolved

**Chain:** Bitcoin
**Cumulative losses:** ~$130M (Galaxy Research revised estimate, August 4 — no material upward revision Aug 7–8)
**Addresses swept total:** 5,900+ confirmed across all attack waves
**Active attacker groups:** 15+

**Day 9 status:** No arrests, no seizures, no voluntary fund returns. The competitive sweeping dynamic remains active — multiple independent groups are racing to drain addresses that fall within the weak-entropy keyspace before rivals do. Galaxy Research's initial 1,367 BTC / ~$88.6M figure was revised upward to ~$130M after additional later waves were identified. The residual exploitable population is unclear.

**Aug 7–8 developments:** No major new technical development. The AI-attribution angle from Days 6–8 has broadened: Ledger and Foundation Passport have both published public statements distancing their entropy initialization from Coldcard's PRNG regression, implicitly confirming the industry treats this as a new attack class — AI-assisted systematic open-source firmware audit collapsing a 5-year vulnerability window. Law enforcement engagement at ~600 flagged attacker addresses (Galaxy / FBI) has produced no visible seizures through Day 9.

**Root cause (unchanged):** March 2021 firmware commit introduced an `#ifndef` guard that checked whether a constant was *defined* rather than whether it was nonzero. Coinkite had defined the guard as zero ("off"), but because zero counts as defined, the build passed and seed generation silently fell through to MicroPython's Yasmarang software PRNG instead of the STM32 hardware TRNG. Result: Mk3 seeds carry ~40 bits of entropy; Mk4/Mk5/Q carry ~72 bits. Standard BIP-39 12-word seeds should provide 128 bits.

**Affected hardware — move funds immediately if not done:**
| Device | Affected firmware | Remediation |
|---|---|---|
| Mk3 | v4.0.0–v5.0.3 | **No patch possible** — hardware TRNG unavailable on Mk3. Move all funds to a new seed on different hardware. |
| Mk4 / Mk5 | < v5.6.0 | Update to ≥ v5.6.0 **and** generate a new seed and migrate funds. Firmware update alone is insufficient. |
| Q | < v1.5.0Q | Same: update then rotate seed. |

**Bug class:** key-management

## 2. 🟡 New disclosed findings / techniques

### "Vendor Partial-Patch" Oracle Pattern — Supra Fixed 11 Chains, Left Hedera Exposed ($9M, July 11)

**What it is:** On July 11, 2026, Bonzo Lend (Hedera's largest lending protocol, ~$12M TVL) was drained of $9.05M after an attacker submitted a manipulated price update to the protocol's Supra oracle contract using a **zeroed-out committee signature**. The Supra verifier accepted the invalid submission because the signature-validity check was not executing correctly — a critical oracle verifier bug.

**Attack mechanics:** Attacker deposited 250 SAUCE tokens (~$0 real value), submitted a forged price update artificially inflating SAUCE's price, then borrowed 6.63M USDC and 34.52M WHBAR (collateral value ~$0 actual). Protocol TVL dropped 77% instantly; Hedera network-wide TVL fell ~40% in 24h.

**The critical detail:** Supra had already patched the same verifier flaw on **11 other chains** before the Hedera exploit. The fix existed and was deployed. Hedera was not included in the patch rollout. Bonzo Lend and every other Supra-integrated protocol on Hedera was never notified and never received the update.

**Why this is a hunting pattern, not just a past incident:**
The "vendor partial-patch" pattern is reproducible and broadly applicable. Oracle and bridge providers frequently deploy fixes chain by chain rather than simultaneously. Any protocol using Supra (or any oracle provider) should verify the *deployed verifier bytecode* on their chain matches the provider's current canonical patched version. If it doesn't, test whether the verifier accepts submissions with zeroed-out or empty committee hashes — if yes, every protocol downstream of that oracle is exposed to a similar $9M+ drain.

**Generalizes to:** Any protocol using Supra oracles on non-major chains (check Hedera, Fantom, Cronos, etc.), and more broadly any oracle provider that publishes changelogs showing security fixes without confirming universal deployment.

**Bug class:** oracle-manipulation, unverified-contract

### Active Hardhat-Impersonation npm Campaign — Mnemonic / Private Key Exfiltration via hreInit()

**What it is:** A sustained supply-chain campaign (distinct from CHAINDROP) is publishing npm packages with names that closely spoof official Hardhat / Nomic Foundation plugins. Examples include `@nomisfoundation/hardhat-configure`, `@monicfoundation/hardhat-config`. Once installed, packages call `hreInit()` and `hreConfig()` to hook into the Hardhat Runtime Environment and extract private keys and mnemonics from the developer's `hardhat.config.js`, then exfiltrate them AES-encrypted to attacker-controlled endpoints. C2 addresses are resolved dynamically from Ethereum smart contracts — borrowing the same dead-drop technique used by CHAINDROP.

**Scope:** Not limited to development machines — CI pipelines that run `npm install` on affected packages will also expose any keys stored in CI secrets or project `.env` files.

**Not to be confused with CHAINDROP**, which compromises legitimate upstream packages via a self-propagating worm. This campaign publishes net-new typosquat packages. Both campaigns are active simultaneously. Combined, they represent the highest supply-chain threat level to Solidity developers since the event-stream incident.

**Bug class:** supply-chain, key-management

## 4. 🎯 Hunt hooks

**1. Pre-mortem: Hunt abi.encodePacked signature-replay in bridge authorization paths — do it today.**
The Wanchain post-mortem drops within 24–72h. Once it does, this hunt saturates. In any bridge or cross-chain messaging contract in your scope, grep for `abi.encodePacked` calls where fixed-width fields (`address` = 20B) are packed alongside variable-length fields (`string`, `bytes`, dynamic arrays) and the packed result is passed to `keccak256` for signing. Confirm non-injectivity: can two different combinations of field values produce an identical packed hash? If yes, and if the result sits in a validator signature check, file as CRITICAL. The Wanchain exploit achieved 65,000× value amplification — 3,110 NIGHT authorized on BNB → 203M+ NIGHT withdrawn on Cardano — from a single valid signature.

**2. Supra oracle partial-patch scan: verify deployed verifier bytecode against current canonical version.**
For any target protocol using Supra oracles, retrieve the verifier contract address from the Supra oracle proxy on that chain. Compute the bytecode hash and compare to Supra's documented current version. If there's a mismatch (older bytecode), run a local fork test: call the verifier's proof-validation function with a zeroed-out or empty committee signature and valid price data. If the call succeeds (returns rather than reverts), every protocol downstream of this oracle is exposed to the Bonzo Lend attack pattern. This works on Hedera, BNB Chain, Fantom, Cronos, and any chain where Supra deployed before the July 2026 patch wave. File as CRITICAL with direct reference to the Bonzo Lend precedent and the Supra partial-deployment CVD failure.

**3. Audit project dependencies for Hardhat typosquats — rotate keys if any are found.**
Run `npm ls 2>/dev/null | grep -E "@nomi[^c]|@monic|@nomicfou[^n]"` in every Hardhat project directory. Any package from an org name that isn't `@nomicfoundation` is a red flag. If a match is found: (a) treat all private keys and mnemonics ever loaded in that project's `hardhat.config.js` as compromised, (b) rotate CI secrets, (c) audit recent contract deployments from those keys for unauthorized transactions, (d) report to the affected protocol's security team as part of your responsible disclosure. For bug bounty programs specifically, any protocol whose CI pipeline installs a Hardhat typosquat is exposing deployment keys — that's an in-scope finding on most Immunefi-listed programs under "Key Management / Infrastructure."
