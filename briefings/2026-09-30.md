### DYORSWAP — Fake "GIWA Mainnet" Bridge Impersonation, ~$2M ETH

**Chain:** Ethereum (DYORSWAP DEX); the fraudulent network impersonated GIWA, an Ethereum L2 built by Upbit operator Dunamu whose mainnet has **not actually launched**.
**Status:** CONFIRMED, funds lost and laundered. First reported **Sept 27-28** (sources differ by about a day on exact hours; DYORSWAP itself has not disputed the ~$2M figure). This is the first appearance of this incident in this briefing series.
**Impact:** **~$2M** — 767.65 ETH deposited by 1,333-1,335 wallets, with 766.25 ETH drained in a single transaction. DYORSWAP has since paid out **200+ ETH** in compensation, reportedly covering smaller victims at a partial rate.
**What happened:** Scammers stood up a fully-featured fake blockchain replicating GIWA's *planned* (not yet live) mainnet — matching its publicly documented Chain ID (9134), and standing up a working RPC endpoint plus an OP-stack-style bridge and batcher. DYORSWAP integrated this network believing it was the genuine GIWA mainnet and enabled bridging against it. Per Protos' timeline, the fake bridge went live roughly 6:00 PM UTC Sept 27, accumulated deposits for about 12 hours, then was drained around 6:30 PM UTC Sept 28 via a single transaction, with proceeds routed through Tornado Cash before DYORSWAP could react. GIWA's real operators (Dunamu) publicly stated no mainnet RPC exists and that circulating "mainnet connection details" were fabricated — their documentation lists only GIWA Sepolia (a different chain ID).
**Root cause:** Not a smart-contract logic bug in an audited protocol — a **counterparty-verification failure**: DYORSWAP accepted an unverified, attacker-controlled network as a legitimate pre-launch mainnet because the fake chain reproduced enough public pre-launch metadata (chain ID, a plausible RPC, bridge contracts) to pass surface-level checks.
**Bug class:** social-engineering / chain-impersonation (fake L2 + spoofed chain ID; integration/verification failure on the DEX side, not a contract vulnerability in GIWA or DYORSWAP's own code).

### Zano — Gateway Address Unauthorized Minting, Chain Rolled Back ~1 Month

**Chain:** Zano (privacy-focused, CryptoNote-based L1)
**Status:** CONTAINED via emergency chain rollback. First disclosed **~Sept 27-28**; this is the first appearance of this incident in this briefing series. No technical post-mortem published yet — Zano's team has explicitly promised one but has not set a date.
**Impact:** **Undisclosed.** Zano has not published a dollar figure or token count for the unauthorized ZANO/Freedom Dollar (fUSD) minted, describing the total only as "considerable." ZANO's price fell roughly 12-13% around the disclosure (market cap ~$97.6M at report time). Treat any inferred dollar amount as unconfirmed until Zano publishes numbers.
**What happened:** A bug in "Gateway Addresses" — a feature shipped in Hard Fork 6 (block 3,833,000, **Aug 26, 2026**) that gives exchanges, bridges and payment processors an account-style balance instead of Zano's normal UTXO model — allowed unauthorized ZANO and fUSD to be minted without limit. The flaw went unnoticed for roughly a month. Zano's response was to roll the entire chain back to block 3,833,000 (immediately pre-Hard-Fork-6), erasing about a month of legitimate transaction history along with the unauthorized mints, and requiring every node, miner, staker and exchange to install software v2.2.3.600 to follow the recovered chain. The team says wallet spend keys and the privacy transaction system itself were never touched, and that assets already converted off-chain to USDT/DAI/etc. on other networks cannot be clawed back by the rollback.
**Root cause:** Asset-issuance logic flaw in the Gateway Address feature, allowing minting outside normal consensus-enforced supply constraints; exact mechanism not yet disclosed pending Zano's technical report.
**Bug class:** access-control / asset-issuance-logic (unbounded minting via a privileged account-style balance feature bolted onto a UTXO chain).

## 4. 🎯 What to hunt

**1. Chain/network-integration verification for DEXs, bridges and aggregators (sharpened by DYORSWAP/fake GIWA)**

A DEX integrated an entire fake blockchain — RPC, bridge, batcher, and a chain ID matching public pre-launch documentation — because it looked sufficiently real on cursory inspection. For any protocol that lets users bridge to or trade against a "new" or "upcoming" chain, check what the integration's trust anchor actually is: is chain-ID matching treated as sufficient verification, or is there an out-of-band check against the real project's official channels/DNS/contracts before a new network goes live in production? Any project preparing to list a pre-launch L2/L1 is a target for exactly this attack.

**2. Privileged "convenience" balance/minting features bolted onto supply-capped chains (Zano Gateway Addresses)**

Zano's UTXO-based, fixed-supply chain shipped an account-style balance feature for exchange/bridge convenience, and it broke the base chain's core supply invariant for about a month before anyone noticed. When auditing any L1/L2 that adds an "easier integration" code path (batch APIs, account abstraction shims, custodial-style balances) on top of a different underlying accounting model, explicitly test that the new path cannot violate the invariants the base model guarantees — supply caps, UTXO uniqueness, etc. — under adversarial input, not just the happy path the feature was designed for.

**3. Third-party/vendor components inside the transaction-approval path (Bitget, still unresolved)**

Unchanged guidance: for custody, multisig, or MPC systems in scope, map every third-party product with credential-issuing or write access upstream of signing. Bitget's outstanding vendor report (promised "this week," still not delivered) is itself informative — a vulnerability disclosure that stretches this long usually means the fix is more invasive than a config change.

**4. Marketplace/UI-level mitigations papering over unpatchable contract bugs (Magic Eden/Limit Break)**

Unchanged: Payment Processor V2 remains callable by anyone, forever, on every chain it's deployed to, independent of the new claim site for rescued NFTs. Any other integrator of the same unpausable contract remains fully exposed.

**5. Post-mortem latency as its own signal**

Bitget, Neutron, Payy, Meter.io, Blink, Zano and DYORSWAP are all now carrying promised-but-undelivered technical write-ups, several a full week or more overdue. Don't wait on official post-mortems to reason about root cause from on-chain evidence and third-party analysis — the underlying bug classes are already public knowledge.

**6. Governance-cost-to-TVL ratio in Cosmos-SDK/CosmWasm chains (Neutron, Day 8)**

Unchanged: for any CosmWasm protocol in scope, calculate the ratio between the cost of winning a governance vote at spot price right before tally and the value of assets that vote's outcome can control, and check for timelocks between proposal tally and execution.

**7. Client-side signing implementations in hardware/software wallets — treat early figures as a floor (DCENT, Day 16)**

DCENT's XRP leg is now over two weeks old with the signing-compromise mechanism still undisclosed. Prioritize signing/key-derivation code review in any hardware or mobile wallet audit.
