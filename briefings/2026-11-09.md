### ACryptoS — Vault Share-Minting Exploit, ~$665,000, Project Shutting Down

**Chain:** Multi-chain DeFi yield aggregator; the exploit affected 77 vaults across 5 blockchains (not individually named in reporting reviewed).
**Status:** Active fallout. Deposits disabled; withdrawals left open. The project states it can no longer maintain itself and has effectively ceased operations.
**Impact:** Approximately $665,000 in total losses, per ACryptoS's own disclosure.
**What happened:** On or shortly before Nov 9, 2026 (exact exploit timestamp not disclosed in reporting reviewed), an attacker exploited a lack of input validation in ACryptoS's vault contracts to mint the vast majority of a vault's shares by depositing only a minimal amount of tokens — effectively diluting existing depositors and then redeeming the inflated share balance against real vault assets. The attack was not confined to one vault: it hit 77 vaults spread across five chains.
**Root cause:** Missing input validation on the deposit-to-share-minting path, allowing a disproportionate share mint from a trivially small deposit.
**Remediation:** Deposit functionality disabled across affected vaults; withdrawals kept open so users can exit. ACryptoS publicly offered the attacker a 10% bounty (roughly $66,500) for voluntary return of funds.
**Attribution:** None disclosed. The stolen funds have reportedly been moved through multiple cross-chain protocols; no attacker address has been published in the reporting reviewed.
**Bug class:** Missing/insufficient input validation on a vault's share-minting logic — a variant of the classic "first depositor" / inflation-attack class, but triggered via a minimal, not first, deposit.

### Loopscale — Correction: Nov 5 Incident Included a Genuine On-Chain Exploit, Not Just DDoS

**Chain:** Solana.
**Status:** Correction to the prior edition. The Nov 8 briefing described the Nov 5 Loopscale pause as resolved and attributed entirely to "a volumetric API/DDoS-style campaign, not a smart-contract or on-chain logic bug." Nov 9-dated reporting makes clear that characterization was incomplete: a genuine, successful on-chain exploit also occurred during the same window, alongside the high-volume API campaign.
**Impact:** The exploit itself extracted real funds: an attacker borrowed and bridged out **4,597 SOL (~$412,000)**. A second, larger attempt — an inflated-NAV redemption targeting roughly **$521,000** from the USDC Genesis Vault — was caught and halted within 30 seconds, resulting in no loss on that attempt. Loopscale states the affected vault was subsequently made whole via liquidation of the attacker's bad loan position (~4,598.4 SOL); who funded that liquidation is not disclosed in reporting reviewed, so "no user-deposit loss" is accurate as an end state but should not be read as "no exploit occurred."
**What happened (technical):** The attacker deposited a single kySOL token worth roughly $120, but labeled the position as an **Orca collateral type** rather than a standard SPL position. Under Orca's collateral rule, the kySOL mint was permitted to differ from a zBTC price-identifier — a check that would otherwise have required the mint and the price identifier to match. kySOL uses 9 decimals (like SOL); zBTC uses 8. Reading one kySOL's raw base-unit balance through zBTC's 8-decimal price entry computed to "10.0" zBTC. The attacker then borrowed 4,597 SOL against that fabricated ~10 zBTC valuation and bridged the SOL out to paired EVM addresses before the position could be caught. Separately, this correction does not negate that a high-volume (30,000+ requests/day) malicious API campaign against Loopscale's SOL and USDC Genesis Vaults was also underway around the same period, as reported previously — both appear to be real, and reporting reviewed does not establish whether they were coordinated by the same actor.
**Root cause:** A collateral-type/price-identifier mismatch check that Orca-labeled positions bypass, combined with a 9-decimal-vs-8-decimal asset mismatch that let a trivial deposit be valued roughly 80,000,000x above its real worth (10 zBTC vs. ~$120 of kySOL).
**Remediation:** Bad loan liquidated; vault restored; full deposit/withdrawal/loan-management functionality for all vaults resumed Nov 8 as previously reported. A formal technical post-mortem remains pending — Loopscale has not yet disclosed the fix applied to the collateral-type validation logic.
**Attribution:** None disclosed.
**Bug class:** Decimal-mismatch collateral-identity confusion — a price oracle/collateral-type validation gap, not a DDoS. This is the bug class worth sweeping for: any protocol that lets a "collateral type" label (e.g., "Orca position," "Beam account") bypass a mint-identifier-matches-price-identifier check is vulnerable to the same pattern regardless of which specific tokens are involved.

## 4. 🎯 What to hunt

**1. Collateral-type labels that bypass mint-identifier validation (Loopscale correction, this window)**

The real lesson from today's Loopscale correction isn't "DDoS happened" — it's that a specific collateral-type label (Orca) was allowed to skip a check that every other collateral type enforced (mint must match the price-feed's asset identifier). Combined with a decimal-count mismatch between the deposited token and the asset it got priced as, a $120 deposit was valued at ten Bitcoin. If you're auditing any lending/vault protocol that supports multiple "collateral type" or "position type" tags feeding into the same oracle-pricing path, check every type for this exact class of gap: does each type independently re-verify that the asset actually deposited matches the asset being priced, or does at least one type trust the caller's label? Also check decimal normalization at every price-lookup boundary, not just at deposit.

**2. Vault/share-minting input validation on minimal deposits (ACryptoS, this window)**

A classic inflation-attack variant: ACryptoS's vaults let an attacker mint the "vast majority" of a vault's shares by depositing only a trivial amount. If you're reviewing any ERC-4626-style or custom vault-share contract, specifically test minimum-deposit edge cases and first-mint/near-empty-vault share-price math — this bug class keeps recurring across different implementations because each team re-derives its own share-minting formula rather than reusing an audited reference.

**3. Self-hosted wallet software with extension/plugin ecosystems as an underexamined attack surface (LNbits, this window)**

LNbits' core-vs-extension ambiguity — a wave of attacks against account-creation and withdrawal functions, with the team unable to say within 24 hours whether the bug lives in core code or a specific extension (Paywall, initially) — is a reminder that any wallet platform supporting third-party or optional extensions needs its core account/authorization boundary to hold even when an extension is buggy or malicious. If you're auditing Lightning-adjacent or any plugin-extensible wallet software, map exactly which privileges an extension can exercise against account-creation and withdrawal paths, and whether the core enforces limits independently of what an extension requests.

**4. Independent on-chain loss trackers double-counting a vendor's own whitehat rescue transactions (Keplr/Web3Auth, this window)**

The Bitquery/Web3Auth overlap (all eight "thief" addresses tagged by Bitquery are also Web3Auth's own recovery addresses) is a methodological trap worth internalizing for anyone doing on-chain forensics during an active incident: address clustering that labels "funds moving away from victim wallets" as theft will misattribute legitimate rescue operations as additional loss, especially when the rescuer deliberately mimics the attacker's own path (as Web3Auth did here, by design, to move faster than the attacker). When reporting or consuming a loss figure during an active whitehat-recovery operation, check whether the cited "attacker" addresses have been cross-referenced against the vendor's own published recovery-address list before treating the figure as a clean loss total.

**5. Logging quiet, confirmed-stable incidents accurately rather than letting "resolved" calcify an incomplete narrative (process note, this window)**

The Loopscale correction exists because the prior day's "resolved, DDoS-only" framing was taken at face value from early reporting that hadn't yet surfaced the technical post-mortem details. For hunters and trackers alike: an exchange or protocol's own "no user funds lost" statement can be true as an end state while still concealing that a real exploit occurred and was quietly made whole — worth re-checking any protocol's "we got DDoS'd, nothing to see here" statement once more technical detail becomes available, rather than closing the file.
