> **Scope:** Multi-chain (EVM/Solidity · Solana/Rust · Cosmos/Move · cross-chain bridges). Priority: DeFi, wallets, key infrastructure.

## 1. 🔴 Active exploits (last 24h)

### Base Vault (protocol unidentified) — Safe-Whitelist Re-Toggle Exploit, ~$6M wstETH stolen (+ ~$31.7M at risk)

**Chain:** Base (Ethereum L2). Vault contract `0xD1895f2019c2152FC2b9022D57f19198c4CFCABC` (a TransparentUpgradeableProxy), controlled by a 3-of-7 Safe multisig at `0x6b27512a5943Ed327f6cb6C3EC1f0398229f42C4`. The vault lent through Aave V3 on Base; Aave's own core contracts and Base itself were not compromised.
**Status:** CONFIRMED on-chain (multiple blockchain-security firms — Blockaid, PeckShield, CertiK — independently alerted), but **no protocol or team has publicly claimed the vault or the loss**, and no post-mortem exists. The vault's Safe had not executed any transaction in the prior 25 days before this incident.
**What happened:** At 08:52 UTC on Oct 4, the vault's Safe removed a newly deployed, attacker-controlled contract from the vault's Aave-lending whitelist. One minute later, at 08:53 UTC, the same Safe re-added that exact contract to the whitelist — both transactions carried valid ECDSA signatures from existing signers. Roughly 70 seconds after re-whitelisting, the contract borrowed 1,783 aBaswstETH (Aave V3's interest-bearing Base-wstETH receipt token) from the vault, moved it to an attacker-controlled address (`0x0B5126e1bc27C0de77e02e97945760A674EdB034`), and redeemed it through Aave V3 for the underlying wstETH. Blockaid's first alert came at 09:20 UTC; the loss grew from an initial ~$2M to roughly $6M across six withdrawal transactions over about 40 minutes.
**Root cause:** Unconfirmed. The two Safe transactions (de-whitelist, then re-whitelist) both carry legitimate signer signatures, so the failure is not a smart-contract logic bug in Aave or the vault's core lending code — it is an authorization-process failure somewhere upstream of the Safe (compromised signer keys, a manipulated signing/approval workflow, or insider collusion are all raised as possibilities by reporting, with none confirmed).
**Bug class:** access-control (multisig/whitelist authorization-process compromise; exact vector undisclosed). Reporting describes this as the fourth Aave-linked exploit on Base within a week — this briefing has independently tracked only this incident and the separate Oct 1-2 FlashLoopAdapter exploit (see below), so that count is attributed to the source, not independently verified here.

### Aave v3 — FlashLoopAdapter / Loop Safe Module Access-Control Exploit, ~114.09 ETH (~$305K) (Day 5)

**Chain:** Ethereum (third-party "Loop Safe Module" adapter used alongside Aave v3 and Safe multisig wallets; Aave's and Safe's own core contracts unaffected).
**Status:** UNRESOLVED. The Oct 3, 18:00 UTC whitehat-bounty deadline (keep 11.41 ETH, return 102.69 ETH) passed two days ago with no public confirmation found of whether the attacker accepted, returned funds, or let the offer lapse — still no resolution as of this writing.
**Root cause (unchanged):** FlashLoopAdapter's `open()`/`close()` functions verified callers only via `ISafe(msg.sender).isModuleEnabled(address(this)) == true` — spoofable with a forged Safe contract that always returns true — combined with an unrestricted arbitrary-call `_swap()` path.
**Bug class:** access-control (trusting a module-enabled check as caller-identity proof, plus unrestricted arbitrary-call path).

## 4. 🎯 What to hunt

**1. Multisig whitelist/approval toggles as an attack primitive, not just a config action (Base vault, new this window)**

The core anomaly here isn't a smart-contract bug at all — it's two consecutive, validly-signed Safe transactions (remove attacker contract from whitelist, re-add it 60 seconds later) that no one claims to have intended. For any audit touching a Safe-gated vault, lending whitelist, or module-permission list: don't just check that the access-control logic is correct — check who can change the list, how fast changes can be made after a long period of inactivity (this Safe had been dormant 25 days), and whether there's any delay/timelock between a whitelist change and that address being usable. A permissions list that can be toggled and exploited inside a single block is operationally equivalent to no permissions list.

**2. Hook/rebalance logic that fails to isolate protocol-injected liquidity from caller input (MALT, GoldPesa — still unconfirmed by either team)**

Unchanged from the last two editions: a swap or liquidity-management function that calls an external hook mid-transaction (rebalance, netting, repayment) and then checks only the resulting balance, not who actually supplied each unit of value. Any protocol using Uniswap v4 hooks or similar flash-accounting rebalancing callbacks should verify this explicitly.

**3. Recovery-rate realism vs. attribution headlines (Bitget, Day 12)**

Still only ~$1.1M frozen of $387.5M despite a formal DPRK attribution. Attribution confidence and fund-recovery likelihood remain separate axes for any exchange/custody risk assessment.

**4. Third-party adapters/modules bolted onto audited core protocols (Aave FlashLoopAdapter, Day 5)**

Unchanged: a helper contract trusting a cheap boolean (`isModuleEnabled`) as a stand-in for caller identity, paired with an arbitrary-call path. The victim's on-chain whitehat bounty offer (90% return, 10% keep, hard deadline) remains a useful template to know — note that in this case, the deadline came and went without any public resolution, which is itself a data point on how often these offers actually get taken.

**5. Post-mortem latency as its own signal (standing)**

Meter.io, DCENT, Fetch.ai, MultiversX, Blink, GoldPesa and MALT still have no primary team write-up, several now weeks overdue. Don't wait on official write-ups to reason from on-chain evidence; also don't assume "no write-up yet" means "nothing happened" — re-check periodically, since Payy's real post-mortem sat unnoticed for several days before being picked up in this briefing series.
