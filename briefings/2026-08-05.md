### Coldcard Firmware PRNG — 15 Independent Attackers, ~$130M Cumulative (Day 6)

**Chain:** Bitcoin  
**Cumulative losses (waves 1–4+):** ~$130M (Galaxy Research revised estimate, Aug 4 UTC)  
**Addresses swept total:** 5,900+ across all known waves  

**Critical new development (Aug 4–5 UTC):** Galaxy Research reports the sweep operation has fundamentally changed character. What began as a small number of apparently coordinated sweeping scripts in Waves 1–3 has fractured into **at least 15 separate, independent attackers** now simultaneously enumerating and draining vulnerable address space. The attack surface is now effectively an open market — any party with access to the public vulnerability details and sufficient compute can reconstruct private keys for affected seeds and join the race.

**Dormant wallet panic signal (Aug 4 UTC):** On-chain analysts (Lookonchain) flagged that a 12-year-dormant Bitcoin wallet, labeled `18TExP`, moved 500 BTC (~$31.3M) that had been inactive since 2013. This is NOT confirmed as a Coldcard-originated wallet — the coins predate the affected firmware by a decade — but analysts attribute the move to the holder proactively rotating keys out of Coldcard-panic. This is consistent with a broader retail wave: BTC retail transfers to centralized exchanges hit **FTX-era highs** this week, as individual holders who cannot confidently rule out Coldcard exposure move funds to custodial safety.

**Attacker profile shift:** The fragmentation from coordinated to competitive sweeping increases the urgency for remaining vulnerable wallet holders — the attacker pool is now larger, more diverse, and motivated by competitive first-mover incentives. Any Coldcard-generated seed in the vulnerable entropy range that has not yet been swept should be treated as actively at risk today.

**Affected versions (unchanged — see Aug 1–4 briefings for full technical detail):**
- Mk3 (firmware v4.0.0–v5.0.3): **no patch exists; move funds immediately**
- Mk4 / Mk5: firmware before v5.6.0 — update then rotate seed
- Q: firmware before v1.5.0Q — update then rotate seed

**Reminder:** Updating firmware does not secure an already-compromised seed. Move funds to a fresh seed generated on patched hardware.

**Bug class:** key-management

## 3. 🟢 Advisories / CVEs

### XRPL xrpld 3.2.1 — Manifest Flood DoS Patched (Node Operators: Upgrade Now)

**Affected software:** `xrpld` < 3.2.1 (XRP Ledger node daemon)  
**Severity:** MEDIUM-HIGH (DoS / resource exhaustion — no fund loss, no consensus failure, but unpatched nodes exposed to flooding attacks)  
**Disclosed:** ~July 31 (incident observed); August 1–2 (hotfix released and advisory published)  
**Status Aug 5:** Broadly deployed, but node operators are still completing upgrades — unpatched nodes remain exposed.

**The vulnerability:** Before v3.2.1, XRPL nodes accepted, stored, and propagated an unlimited number of validator manifests from unknown (unrecognized) validator public keys. An attacker could flood a node with high volumes of manifests from junk keys, consuming storage, CPU, and bandwidth. Manifests were also persisted to disk, meaning they survived node restarts.

**What 3.2.1 adds:**
1. Oversized manifests rejected before full decoding
2. Incoming manifest batches per network message capped
3. Volume of manifest data relayed to new peers limited
4. Unknown validator manifests no longer persisted to disk (cleared on restart)

**Action required:** Node operators running `xrpld` < 3.2.1 should upgrade. Two-step process: install 3.2.1, then restart. No on-chain action needed.

**Bug class:** dos

## 4. 🎯 Hunt hooks

**1. Protocol admin multisigs: audit hardware wallet provenance before Wanchain deadline creates further distractions.**  
The Coldcard sweep is now a 15-attacker open competition, meaning the pace of remaining address sweeps will only increase. The highest-value targets that haven't been publicly checked are **protocol admin keys, upgrade guardians, pause-function signers, and DAO multisig participants** who used Coldcard hardware during the affected firmware window (March 2021 onward). For any bug-bounty target: search their Discord/docs/deployment notes for mentions of Coldcard, Mk3, Mk4, or Mk5. Even a 4-of-7 multisig with one or two compromised Mk3-derived signers has measurably weakened security. File it as informational at minimum; depending on multisig threshold, it could be CRITICAL.

**2. Grep target P2P/networking layers for unbounded acceptance of external data from unknown peers.**  
The XRPL manifest-flood DoS (xrpld < 3.2.1) is a clean example of a class of vulnerability that appears across blockchain node implementations: **unbounded resource consumption triggered by data from unauthenticated/unknown sources**. In any L1/L2 node codebase in your scope, look for:
- Message handlers that accept, deserialize, or store objects from unknown peer IDs before any allowlist/reputation check
- Any data structure (map, list, disk store) that grows without a configured cap based on external input
- Network message types that accept large batches (`manifest_batch`, `tx_set`, `peer_shard_info`, etc.) without per-sender rate limits

File resource-exhaustion DoS bugs against node software at MEDIUM-HIGH if exploitation can knock a validator offline; HIGH if it can be sustained to partition the network.

**3. Wanchain signature amplification pattern — hunt for `abi.encodePacked` with variable-length mixed-type fields in any bridge in scope.**  
The Wanchain deadline expires in hours; this is a good moment to apply the pattern to new targets before the post-mortem drops and everyone is looking at it. Grep target: `abi.encodePacked` calls that combine `address` (20B fixed), `uint256` (32B fixed), and ANY of `string`, `bytes`, `bytes32`, or multiple consecutive `uint` fields where field count ≥ 3 and the result is used as input to `keccak256` before signing. Confirm exploitability by checking if an attacker can supply different field lengths that hash to the same packed bytes. File as HIGH if found in a bridge authorization path.
