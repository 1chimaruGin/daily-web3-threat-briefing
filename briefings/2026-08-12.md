### Coldcard Bitcoin Hack — Day 13: No New Wave, But Ecosystem Audit Shows Damage Is Deeper

**Chain:** Bitcoin
**Cumulative losses:** ~$130M+ / ~2,055 BTC across four waves (July 30 – Aug 3)
**Status:** No confirmed Wave 5 in the Aug 10–12 window. Attacker activity has quieted significantly, with most newly swept BTC remaining stationary at consolidation addresses — the market for offloading 2,055 BTC without triggering exchange freezes is limited. FBI and DOJ involvement confirmed (Aug 5). Coinkite has committed to a compensation framework for victims, details pending.

**Day 13 key development:** The Bitcoin Red Team — a coalition of security researchers organized post-disclosure — published its findings from a 30-hour ecosystem scan. Across 390 Bitcoin-ecosystem projects (wallets, signing libraries, hardware interfaces, PSBT implementations), they filed approximately 4,962 security findings, of which:
- ~85 rated critical (arbitrary key extraction, seed reconstruction, weak entropy provable offline)
- ~635 rated high (insecure RNG seeding, deterministic nonce bypass, missing hardware TRNG assertions)

The most common critical pattern: software PRNG fallback on entropy-source failure without explicit error, identical to the Coldcard flaw. Several open-source wallet SDKs use a "best effort" entropy model where a failed `getrandom()` syscall silently falls back to `time(NULL)` or similar — seeds generated on affected systems are cryptographically recoverable.

**Ongoing remediation status (by device):**

| Device | Affected firmware | Action required |
|---|---|---|
| Coldcard Mk3 | v4.0.0 – v5.0.3 | Move ALL funds to new device + new seed (no firmware fix possible) |
| Coldcard Mk4 / Mk5 | < v5.6.0 | Upgrade to ≥ v5.6.0 AND generate new seed + migrate funds |
| Coldcard Q series | < v1.5.0Q | Upgrade to ≥ v1.5.0Q AND generate new seed + migrate funds |

Seeds created via the **dice-roll entropy entry option** are NOT affected — this path bypasses the software PRNG entirely.

**Bug class:** key-management

### BTCPay Server LND Macaroon Auth-Bypass — Day 5: Responsible Disclosure Bounty Paid; Unrotated Credentials Still Live

**Chain:** Lightning Network (Bitcoin)
**Status:** No new confirmed drains in the Aug 11–12 window. Patch v2.4.2 remains the fix for the exploitable Greenfield API endpoint exposure. BTCPay Server donated 0.42 BTC to the responsible security researcher who privately reported the vulnerability before it was publicly exploited — the window between private report and first observed in-the-wild exploitation was less than 72 hours, suggesting a second independent attacker chain discovered the bug concurrently.

**Critical residual threat (unchanged):** Stolen LND macaroon files (`admin.macaroon`, `invoice.macaroon`, `readonly.macaroon`) do not expire. Any node that was externally accessed before patch deployment retains a live, full-admin credential in attacker hands. Patching the server does NOT revoke those credentials. Operator rotation rate remains low — most small Lightning nodes run unmonitored; without an alert, operators don't know they were hit.

**Checklist for operators (still outstanding for many):**
1. Confirm BTCPay Server ≥ v2.4.2 is running.
2. Check macaroon file timestamps in `~/.lnd/data/chain/bitcoin/mainnet/` — if files predate Aug 7 00:00 UTC, they were NOT regenerated by the patch and a live admin credential exists.
3. Hard-rotate: stop BTCPay + LND → delete `admin.macaroon`, `invoice.macaroon`, `readonly.macaroon` → restart LND (auto-generates new files) → restart BTCPay.
4. Audit LND logs for `SendPayment`, `CloseChannel`, and `ConnectPeer` RPCs issued from unexpected IPs since Aug 1.

**Confirmed victims (from original disclosure):** Foundation (Passport wallet maker), Citadel21 (Bitcoin publication) — both had Lightning channels swept and force-closed before public warning.

## 2. 🟡 New disclosed findings / techniques

### Bitcoin Red Team Ecosystem Audit: 4,962 Findings / 390 Projects — Software PRNG Fallback Is Systemic

**What it is:** Following the Coldcard disclosure, a coalition of Bitcoin security researchers (operating under the informal "Bitcoin Red Team" label) executed a 30-hour coordinated review of 390 open-source Bitcoin-ecosystem projects — wallet SDKs, signing libraries, hardware abstraction layers, PSBT implementations, Lightning implementations.

**Key findings:**
- ~85 critical: Includes three wallet SDKs where a failed `getrandom()` syscall falls back to a low-entropy source (`time(NULL)`, `clock()`) without error — producing cryptographically recoverable seeds identical to Coldcard's failure mode.
- ~635 high: Includes deterministic nonce derivation failures in several ECDSA wrappers and missing assertions on hardware RNG readiness.
- The pattern is: any code that calls an entropy source, checks whether it *returned a value* (rather than whether it returned *sufficient-quality* randomness), and proceeds silently is vulnerable.

**Applicability to EVM/DeFi:** The same class of failures occurs in JavaScript and Rust wallet libraries used in DeFi frontend key generation. Any `ethers.js` or `viem` wrapper that calls `crypto.getRandomValues` without confirming Web Crypto API availability and then falls back to `Math.random()` is in-scope for this pattern.

**Check:** In any wallet or key-generation code, search for: `Math.random()`, `Date.now()` as seed material, `new Uint8Array` filled without `crypto.getRandomValues`, or any entropy call without an explicit check that the returned buffer is not all-zero. All of these indicate a keygen path that can produce recoverable private keys.

### abi.encodePacked Signature-Replay in Bridge Signing Paths — Pattern Now Fully Public

This was disclosed in the Aug 11 briefing but bears repeating as the hunt window has now been open to all researchers for 24h. From Wanchain's post-mortem:

**The flaw:** `abi.encodePacked` on variable-length fields (bytes, string, dynamic arrays) is non-injective — multiple distinct field combinations produce identical byte sequences. If the packed output is hashed and signed, a single valid signature can authorize semantically different transactions.

**How to find it (grep):** `grep -r "abi.encodePacked" --include="*.sol"` → filter for lines inside functions that also contain `keccak256` → check for calls that pass the result to ECDSA verify or a `signedMessages` / `authorized` mapping lookup. Two or more adjacent `bytes`/`string`/dynamic-array parameters without explicit length separators = candidate critical.

**Correct fix:** Replace `abi.encodePacked(a, b, c)` in signing paths with `abi.encode(a, b, c)`, or use EIP-712 (`\x19\x01` + domain separator + struct hash).

## 4. 🎯 Hunt hooks

**1. Software-PRNG keygen fallback — expand the Coldcard pattern to your EVM targets.**
The Bitcoin Red Team audit found the "silent entropy fallback" pattern is common across open-source wallet and signing codebases. For any protocol in your scope that generates keys client-side (web wallets, browser extensions, mobile apps), check the key generation path for: `Math.random()` used as seed material; `Date.now()` or `performance.now()` in seed derivation; `crypto.getRandomValues()` called without checking that the Web Crypto API returned a full, non-zero buffer; or any conditional that silently proceeds when the preferred entropy source errors. A confirmed weak-entropy keygen path is a CRITICAL finding enabling direct user fund theft. This class is actively being hunted post-Coldcard — file fast if you find it.

**2. BTCPay + Lightning — unrotated macaroon scan still in 5-day window.**
Day 5 post-disclosure, many small Lightning operators have patched but not rotated. For any Lightning-facing protocol or merchant in your scope: check the public `/misc/info` endpoint for the BTCPay version (pre-2.4.2 = unpatched = instant CRITICAL, trivially PoC-able). If the version is ≥ 2.4.2, check whether macaroon files were regenerated post-Aug 7 (macaroon file timestamps = `ls -la ~/.lnd/data/chain/bitcoin/mainnet/*.macaroon`). An older admin macaroon accepted by LND is a full-channel-sweep attack with no additional interaction required. This is a direct-financial-impact bug with a clear 3-step PoC: (1) obtain macaroon via directory traversal or backup exposure, (2) `lncli --macaroonpath=stolen.macaroon sendpayment ...`, (3) sweep. File under access-control / key-management.

**3. Windows dev machine lateral pivot — ChainDrop + CVE-2026-68820 attack chain.**
The combination of ChainDrop npm credential theft and the newly-disclosed Windows afd.sys LPE creates a complete code execution → kernel escalation → secrets extraction chain for any web3 team member running Windows dev machines that ran `npm install` after Aug 4. For teams you're assessing: (a) check whether CI/CD runners are Windows-based and unpatched; (b) check whether deployer private keys or multisig signers are on Windows machines that could have run ChainDrop-affected installs; (c) enumerate whether Windows dev machines have direct access to production deployer keystores or hardware wallet signing sessions. A team with both ChainDrop exposure and unpatched Windows dev infrastructure has a plausible full-chain to protocol contract ownership transfer — that's a CRITICAL bug report regardless of which component you technically find.
