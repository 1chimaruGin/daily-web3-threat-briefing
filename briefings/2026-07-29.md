### 2.1 Blockaid H1 2026 Report — Record $1.1B Losses; DPRK Drove 52%; Novel Attack Vectors Confirmed

**Published:** July 28–29, 2026
**Bug classes:** `key-management`, `bridge-dvn`, `access-control`
**Chains:** Ethereum ($332M), Solana ($326M), multi-chain

Blockaid's H1 2026 security report confirms the industry's worst six-month stretch on record: **212 verified security incidents totaling $1.1B+** — more incidents in six months than in all of 2025, and more dollars than any prior H1.

**Key findings:**

- **DPRK attribution:** The two largest single incidents — **KelpDAO ($292M)** and **Drift Protocol ($285M)** — are both attributed to DPRK-linked actors, accounting for ~$577M (~52% of total H1 losses). Both were ultimately key-management and operational security failures, not smart contract code bugs.

- **Attack technique shift confirmed:** Private key theft and phishing now **outnumber smart contract code exploits** as the primary vector driving losses. Human factors — phishing, social engineering, insider access, developer credential compromise — are the dominant loss path. Code bugs are a secondary concern by dollar value.

- **Novel attack vectors confirmed in H1 2026:**
  - **AI prompt injection on developer workflows** — malicious prompts injected into AI-assisted coding or deployment tools cause automated systems to approve malicious transactions or exfiltrate private keys. Blockaid flagged this as a formally validated new class, not theoretical.
  - **Single-DVN bridge compromise** — one malicious or compromised DVN (Dependent Verification Node in LayerZero bridges) can validate fraudulent cross-chain messages with no honest DVN able to override. Altura ($39M, July 4) is the canonical recent live example.

- **Most affected chains:** Ethereum ($332M) and Solana ($326M).
- **Incident count up ~50%** vs. H1 2025 — attackers are hitting more protocols, more often, even as some per-incident dollar values decreased.

### 2.2 GMX V1 Cross-Contract Reentrancy — Full Post-Mortems Now Published

**Incident date:** July 9, 2026 | **Post-mortems published:** Late July 2026
**Bug class:** `reentrancy`
**Chain:** Arbitrum
**Amount lost:** $42M (90% recovered via $5M white-hat bounty)

BlockSec, SlowMist, QuillAudits, and Sherlock have all now published full technical analyses of the GMX V1 GLP pool exploit — the deepest reentrancy post-mortem suite of the month. Worth reading in full if you audit perp DEXes or any protocol with keeper-executed order flows.

**Root cause:** A **cross-contract reentrancy** in `executeDecreaseOrder` within the `OrderBook` contract. The exploit allowed an attacker to re-enter through the `OrderBook` → `PositionManager` call chain, manipulating `globalShortAveragePrice` before state writes were finalized — inflating the protocol's computed AUM and thus the GLP token redemption price.

**Attack flow:**
```
1. Attacker opens short positions to establish baseline state
2. Calls executeDecreaseOrder on OrderBook contract
3. During execution, callback re-enters OrderBook/PositionManager
   via a non-guarded path, modifying globalShortAveragePrice
4. Inflated AUM → GLP price appears artificially high mid-execution
5. Attacker redeems GLP at manipulated price → drains underlying assets
6. Total drain: $42M from Arbitrum GLP pool across multiple assets
```

**Why the guard failed:** GMX V1's reentrancy guard was correct at original deployment. But over four years, the call graph grew — new contracts (`PositionManager`, order keepers) were added that could re-enter the guarded contract via paths that existed *only after* the guard was written. The guard blocked intra-contract reentrancy but was blind to cross-contract callback paths introduced later.

**Critical pattern for auditors:**
```solidity
// The guard on Contract A does NOT prevent this:
// ContractA.functionX() → [guarded] → ContractB.action()
//   → ContractB calls back ContractA.functionY() [NOT guarded entry]
//   → functionY modifies globalShortAveragePrice BEFORE functionX finalizes state
// Result: AUM/price is read after state corruption, before write-back
```

**Outcome:** GMX paid a $5M white-hat bounty (10% of stolen amount); hacker returned $37.8M. GMX finalized a $44M compensation plan for GLP liquidity providers. GMX V2 (separate architecture) was not affected.

### 2.3 BarnBridge Governance Attack — $776K Protocol Takeover for $625

**Incident date:** July 15, 2026 | **Analysis published:** Late July 2026
**Bug class:** `logic-error`, `access-control`
**Chain:** Ethereum
**Amount lost:** ~$776K USDC

The BarnBridge Smart Yield attack is the sharpest "governance liveness" exploit of the month — and the playbook is directly replicable on dozens of dormant DAOs still holding user approvals.

**How it worked:**
1. Attacker acquired and staked enough BOND governance tokens to clear the proposal threshold — at the time, this cost approximately **$625** (token market cap had collapsed; participation was near zero).
2. Passed a malicious governance proposal upgrading the `SmartYield/controller` proxy to a malicious implementation contract.
3. Malicious implementation called `_takeUnderlying()` on `CompoundProvider`, which leveraged **pre-existing USDC approvals from ~50 user accounts** — approvals granted when the protocol was active and never revoked.
4. Total drained: ~$776K USDC across 50 accounts.

**Why this matters — the attack didn't require any code bug:** The proxy upgrade mechanism and the `_takeUnderlying()` approval-drain function both worked exactly as designed. The vulnerability was **governance liveness risk**: a live protocol with active user approvals, but effectively ungoverned at a takeover-viable token price.

**Attack signature:**
- Low-cap governance token + upgradeable proxy = "protocol control for sale"
- Any protocol where `threshold_tokens × price < $10K` is in this risk class
- Pre-existing user `approve(contract, MAX_UINT256)` calls extend the blast radius

## 4. 🎯 Hunt Hooks

### Hook 1: Cross-Contract Reentrancy in Protocols with V1/Legacy Keeper-Executed Flows
*Tied to §2.2 GMX V1 $42M cross-contract reentrancy post-mortems*

The GMX post-mortem is required reading for anyone auditing perp DEXes, order-book protocols, or any system where keeper bots execute orders via multi-contract call chains. The canonical failure: a reentrancy guard written for a smaller codebase that never got updated as the call graph grew.

**What to check in your targets today:**

1. **Find all "keeper-executed" or "bot-executed" order functions** (`executeDecreaseOrder`, `executeLiquidation`, `executeOrder`, `settlePosition`). These typically involve external calls to position managers, vaults, or price oracle adapters.

2. **Map the full cross-contract call graph** for each such function. Ask: after the external call in step N, can any callee re-enter the caller's state-modifying functions via an alternative, un-guarded path?

3. **Check AUM / price calculation timing.** If the protocol reads TVL, AUM, or token price using on-chain state *before* all external calls in the same transaction complete — and any of those external calls can change that state — the price/AUM is manipulable.

4. **Look for the guard-A / callback-through-B pattern:**
   ```
   ContractA.functionX() [guarded] → ContractB.action()
      → ContractB calls ContractA.functionY() [NOT guarded]
      → functionY modifies shared state before functionX finalizes
   ```

5. **Specifically target protocols with V1 pools still holding TVL alongside V2 rewrites.** The old contracts often have guards from an era when the call graph was simpler.

**Report condition:** Cross-contract callback path that can mutate AUM, price, or balance state before the calling function's state write is finalized → **Critical** (GMX-class drain exploitability).

### Hook 2: Dormant-DAO Governance Proxy Takeover — The $625 Attack
*Tied to §2.3 BarnBridge $776K governance attack*

The BarnBridge exploit requires no code vulnerability — just a governance threshold affordable enough for a solo attacker to clear, an upgradeable proxy, and live user approvals. This combination exists today across dozens of protocols launched in the 2020–2022 era.

**What to check in your targets today:**

1. **Find DAO protocols with on-chain governance + upgradeable proxies.** Token-weighted voting (not multi-sig) is the vulnerable model.

2. **Calculate threshold acquisition cost:** `(proposal_threshold_tokens) × (token_price)`. If this is under $50K, flag it. Under $10K, treat as exploitable on-demand.
   - Check Etherscan for `BOND.governance.proposalThreshold()` equivalent in your target.
   - Check recent governance activity — when was the last proposal? A dormant DAO is a vulnerable DAO.

3. **Check user approval surfaces.** Run `eth_getLogs` for `Approval(address,address,uint256)` events targeting the upgradeable contract. Any `approve(MAX_UINT256)` that hasn't been revoked is in the attacker's blast radius.

4. **Focus on protocols that launched V2 but left V1 contracts live with approvals.** The upgrade migration often didn't include a "revoke all approvals" step.

**Report condition:** DAO-governed upgradeable proxy + governance threshold achievable for < $100K + active user `MAX_UINT256` approvals to upgradeable contracts → **Critical** governance takeover with direct fund-drain path.

### Hook 3: DPRK Profile — Which Protocols Fit the Targeting Pattern
*Tied to §2.1 Blockaid report — $577M DPRK H1 attribution (KelpDAO $292M, Drift $285M)*

With DPRK actors now responsible for over half of H1 2026 losses by dollar value, it's worth understanding their target selection criteria — not to predict their next attack, but because their targets are also the best bug bounty targets (high TVL, significant key-management surface, bridge integrations).

**DPRK target selection signals from observed H1 2026 incidents:**

1. **Concentrated TVL in a single vault or clearinghouse contract** — both KelpDAO (restaking vault) and Drift (central clearinghouse) concentrated billions in one contract. Single points of failure with high value = maximum attacker ROI.

2. **LayerZero DVN integration with low DVN count** — enables silent fund routing cross-chain to obscure traces. If your target uses a single DVN (DVN_COUNT = 1), the entire bridge security rests on one validator.

3. **Key-management soft spots** — both top DPRK incidents were key-management failures, not code bugs. Multisig with < 5 signers, no HSM/MPC, signer keys on internet-connected machines.

4. **Recent large VC round or TVL growth** — DPRK observes protocol growth trajectories and hits during scaling phases when operational security lags TVL.

**Your hunt focus:** Any protocol with:
- TVL > $100M in a single contract
- LayerZero integration where you can read `DVN_COUNT` (should be ≥ 2, ideally ≥ 3)
- Multisig controlling upgrade keys with < 5 signers and no timelock
- No hardware security module (HSM) or MPC wallet in use for admin keys

**Report condition:** Single-signer or 2-of-5 (or lower) multisig controlling TVL > $10M with no timelock, OR `DVN_COUNT = 1` in a LayerZero bridge holding real TVL → **High** to **Critical** depending on TVL and exploitability of the entry path.
