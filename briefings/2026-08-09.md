## 1. 🔴 Active exploits (last 24h)

### BTCPay Server — LND Macaroon Auth-Bypass: Lightning Nodes Actively Drained (NEW — Aug 7–8)

**Chain:** Lightning Network (Bitcoin)
**Status:** Actively exploited at time of disclosure; patch v2.4.2 released August 7, 2026.
**Victims confirmed:** Hardware wallet maker Foundation; Bitcoin zine Citadel21. Both had Lightning channels force-closed and funds swept.

**What happened:** An unauthenticated attacker could reach an endpoint in BTCPay Server's Greenfield API that bypassed two-factor authentication and returned `.macaroon` credential files for the co-located LND node. Macaroon files are LND's bearer-credential system — possessing the admin macaroon is equivalent to having full admin access to the Lightning node, including the ability to open/close channels and drain balances without requiring wallet passwords or additional auth.

**Critical post-patch danger:** The v2.4.2 patch closes the API endpoint. **It does NOT invalidate previously stolen macaroons.** LND macaroons are revocable only by deleting the macaroon database and regenerating credentials. Any operator who patched without also regenerating macaroons may still have live admin sessions in attacker hands. BTCPay Server's update process regenerates macaroons automatically on upgrade — but operators who only partially applied the patch or upgraded non-interactively should verify.

**Remediation — immediate:**
1. Update BTCPay Server to ≥ v2.4.2.
2. Confirm macaroons were regenerated: check the LND macaroon directory timestamp or delete and regenerate manually (`lncli bakemacaroon ...` / restart LND with fresh macaroon dir).
3. Audit LND channel state for unauthorized force-closes or unexpected payments since ~August 1 (conservative window).
4. Operators who cannot upgrade immediately: take the BTCPay Server offline until patched; a running vulnerable instance with an active LND node is a full-drain risk.

**Technical note:** BTCPay's Greenfield API is enabled by default for self-hosted instances and is the modern REST API replacing the legacy BitPay-compatible endpoint. The auth-bypass was in how the API handled 2FA enforcement on the credential-export route — 2FA was checked but the response path could be reached without the check completing under specific request conditions. Full technical details withheld by BTCPay team pending broader operator patch uptake.

**Bug class:** access-control, key-management

### Coldcard Bitcoin Hack — Day 10: ~$130M Cumulative, Competitive Sweeping Ongoing

**Chain:** Bitcoin
**Cumulative losses:** ~$130M (Galaxy Research latest estimate; TRM Labs pegs confirmed losses at ~$116M / 1,719 BTC across 5,200+ addresses)
**Status:** No arrests. No seizures. No fund returns. Active sweeping continues.

**Day 10 summary:** The exploit remains the largest hardware-wallet compromise in history. No new technical revelations in the Aug 8–9 window. Multiple independent attacker groups (15+) continue racing to drain addresses within the weak-entropy keyspace. Law enforcement engagement (~600 flagged addresses, FBI / Galaxy) has produced no visible result. The "Bitcoin exploit week" framing is now mainstream: BTCPay + Coldcard running in parallel has put Bitcoin infrastructure security under maximum scrutiny.

**Root cause (unchanged):** March 2021 firmware commit introduced an `#ifndef` guard that checked whether a constant was *defined* rather than whether it was nonzero. Coinkite had defined the guard as zero ("off"), but zero counts as defined — seed generation silently fell through to MicroPython's Yasmarang software PRNG instead of the STM32 hardware TRNG. Mk3 seeds carry ~40 bits of entropy; Mk4/Mk5/Q carry ~72 bits. BIP-39 12-word seeds should provide 128 bits.

**Affected hardware — migrate funds if not done:**

| Device | Affected firmware | Action |
|---|---|---|
| Mk3 | v4.0.0–v5.0.3 | **No patch possible.** Move all funds to a new seed on different hardware. |
| Mk4 / Mk5 | < v5.6.0 | Update to ≥ v5.6.0 **and** generate a new seed and migrate. Update alone is insufficient. |
| Q | < v1.5.0Q | Same: update, then rotate seed. |

## 2. 🟡 New disclosed findings / techniques

### BTCPay Greenfield API Auth-Bypass Pattern — Generalizes to Any LND Control-Plane API

**What it teaches:** The BTCPay exploit highlights a class of vulnerability in Lightning node management layers: API endpoints that act on admin-level credentials (macaroons, passwords, TLS certificates) but where authentication middleware can be bypassed for specific request shapes. This is distinct from the wallet/node logic itself — it's a failure in the HTTP layer sitting in front of LND.

**Where to hunt:** Any self-hosted Lightning infrastructure exposing an HTTP management API — BTCPay, Ride The Lightning (RTL), ThunderHub, LND-Admin — should be reviewed for:
1. Routes that return credential files (macaroons, TLS certs) or accept credential-provisioning requests.
2. Whether 2FA/session-auth middleware runs *to completion* for those routes or can be bypassed by specific request headers, method choices (GET vs POST), or parameter combinations.
3. Whether the API is unintentionally internet-exposed (default Docker port mappings, reverse-proxy misconfiguration).

**Historical parallel:** The BTCPay pattern is structurally similar to authentication-bypass vulnerabilities in banking APIs where a password-reset endpoint skipped the CSRF/auth check because it was added after the middleware chain was configured. In both cases the fix is trivially mechanical but the blast radius is total account takeover.

**Bug class:** access-control, key-management

## 4. 🎯 Hunt hooks

**1. Lightning node control planes: audit HTTP API credential-export routes for auth-bypass.**
The BTCPay exploit class — auth middleware that can be bypassed for credential-returning API routes — is not unique to BTCPay. For any bug bounty scope that includes self-hosted Lightning infrastructure (BTCPay, Ride The Lightning, ThunderHub, LND-Admin), check every route that returns or creates credential material (macaroons, TLS certs, node passwords). Verify that authentication middleware runs *to completion* before the handler returns. Specifically test: (a) requests missing the 2FA header or session cookie — do they 401/403 or silently succeed? (b) routes accessible via GET that are normally POST-only — do method-switching bypass middleware? (c) credential-provision routes accessible without a pre-existing authenticated session. A working auth-bypass on any of these routes is a CRITICAL finding that maps directly to complete node drain, using the BTCPay incident as a proof-of-concept precedent.

**2. Pre-mortem window closes soon: hunt abi.encodePacked signature-replay in bridge auth paths.**
Wanchain's post-mortem is Day 19 with no publication — but it *will* drop, and when it does, this space will be saturated. While the window remains open: grep any bridge or cross-chain messaging contract in your scope for `abi.encodePacked` calls where the packed result feeds `keccak256` for signing. Confirm field non-injectivity: can two different field-value combinations produce the same packed hash? The Wanchain root cause — 14 variable-length fields concatenated without separators — is a pattern that appears in dozens of hand-rolled bridge message encoders. The correct fix is `abi.encode` (which ABI-encodes with type information) or adding explicit length prefixes. A CRITICAL file on any bridge where this pattern permits signature reuse at scale.

**3. Verify macaroon regeneration on any Lightning node your targets run on BTCPay.**
For protocols in your scope that accept Lightning payments via self-hosted BTCPay: check their public infrastructure for BTCPay version banners (the `/misc/info` endpoint returns version info). If they're running < 2.4.2, that's an in-scope critical under key-management / infrastructure access. If they're on 2.4.2 but deployed via CI without an interactive restart, their macaroons may not have been regenerated — test whether admin LND API calls succeed without presenting current session credentials (an orphaned macaroon session from pre-patch still being accepted is exploitable). File under key-management with direct reference to the BTCPay August 2026 incident.
